# devcontour-harness-ui 0.1.0-alpha.7

Панель запускается вместе с трекером задач, до настройки harness, и читает
ревизию представления 5. Peer прежний: devcontour-harness `>=0.1.0-alpha.55
<0.2.0`; новые поля и `--repository` — из devcontour-harness
`0.1.0-alpha.65` (ещё не на npm), с прежними версиями `--state`, `--view` и
`--demo` работают, как раньше. Рекомендуемая пара — devcontour-harness
`0.1.0-alpha.65` и devcontour-harness-ui `0.1.0-alpha.7`.

## Запуск до настройки harness

- `--repository <dir>` — корень проекта вместо `--state`: панель вызывает
  `harness view --repository <dir>`, и harness при каждой проверке сам
  находит состояние и политику в `.harness/project.json`. Её можно
  запустить раньше `harness setup`:

  ```sh
  npx devcontour-harness-ui --repository . --harness node_modules/.bin/harness
  ```

- Пока проекта нет, страница показывает «Идёт настройка harness» и «Задач
  пока нет» (строки harness) и чего ждёт панель — без отказа и без
  предупреждения о связи. Когда проект появляется, страница сама переходит
  к обычным экранам; перезапуск и перезагрузка не нужны.
- Состояние без работ (`stage.name: setup`) — те же строки над экранами.
- `--check --repository <dir>` до настройки — выход 0, `view.setup: "project"`. Если `harness view --repository` отказал (например,
  `POLICY_REQUIRED`: состояние без привязки или нет файла политики), — выход
  3, `compatible: false` и `fix` с сообщением harness: стартовый скрипт не
  поднимет панель, которая покажет только ошибку. Сама страница показывает
  такой отказ как отказ, не как настройку. `--state` работает, как раньше; harness старше
  alpha.65 с `--repository` — отказ с подсказкой про `--state`.
- Экраны, которым хост передал документ без работ и здоровья, показывают
  тот же экран настройки, а не падают; детали работы до настройки — тоже.

## Прогноз всего выпуска

- Процент «До релиза» — по всему выпуску (считает harness), с уже принятыми задачами; строка
  «принято N из M» под заголовком — по тем же числам прогноза, что и круг.
- «Добавлено в выпуск после начала: добавлена задача WEB-3 (задач 2 → 3)».
- «Готовность незаконченных работ» — строка harness и полоса для каждой
  работы («WEB-2: ~60 %, попытка 2 из 3, исправляет замечания»).
- Срок по первым 1–4 попыткам — «осталось грубо, ~25–55 мин (по 2
  попыткам)» с пояснением; «неизвестно» — только когда так говорит harness.
- Законченный выпуск — полный круг «выпуск закончен HH:MM · занял …»;
  прошедшее время больше не растёт (только при `finishedAt`; без него часы
  идут).
- Когда все работы приняты, очередь больше не называется «Очередь стоит» и
  в «Проблемах по ходу» нет пункта «запустить заново»: для законченного
  выпуска никому не нужно запускать harness.

## Нужно от вас

- Принятые работы, оставленные в трекере на проверку человеку
  (`sourceReviews`, эскалация `SOURCE_REVIEW`), — пункт «проверка в
  трекере»: «ждут вашей проверки в Relay: WEB-1, WEB-2», задачи и колонка.
  Они входят в число «Нужно от вас», во фразу «От вас: … проверить N задач
  в источнике задач» и в счёт для экранного диктора; на «Задачах» карточка
  принятой работы говорит «DEMO-1 ждёт вашей проверки в источнике задач
  (колонка review)».
- Запуски, которые не засчитаны в предел, — «(запусков 3, засчитано
  попыток 2)» рядом с попытками.

## Для хостов (встраивание)

- `ViewSource.load()` теперь возвращает `ViewCheck | SetupCheck`, а
  `loadWork()` — `WorkDetailCheck | SetupCheck`: до настройки harness ответ
  может быть `{ ok: true, setup }` (проверяйте `'setup' in check`). Хост,
  который сам реализует `ViewSource` и отдаёт только `ViewCheck`, по-прежнему
  подходит под тип; хост, который читает результат `httpViewSource`, должен
  обработать новую ветку. Новые шлюзы — `checkOverview` и `checkWork`;
  `checkView` и `checkWorkDetail` прежние.
