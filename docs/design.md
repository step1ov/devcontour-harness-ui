Относится к представлению версии 1.

добавлением (`viewRevision`) или новой мажорной версией (§4).

## 1. Цели

Harness работает без интерфейса. Его состояние разнесено по `status`,
`explain`, `report`, `handoff`, записям ревью и журналу событий. Каждая из
этих команд отвечает на один вопрос — в JSON или в тексте терминала.
Оператору, который следит за прогоном, или человеку, на которого работает
ведущий агент, нужно одно место, где видно:

- что ждёт его ответа сейчас;
- что выполняется сейчас, на каком этапе, после скольких попыток и
  перепроверок, и почему была повторная попытка;
- что проверено и как: запуском, повторным использованием прежнего
  результата, чтением reviewer или никак;
- как сходятся ревью: раунды, открытые и решённые замечания, эскалации;
- какие решения приняты по ходу работы, в том числе временные;
- кто что делал: ведущий, harness, writer, reviewer, оператор;
- какие настройки действуют: кто пишет, кто проверяет, пороги, бюджеты,
  таймауты, решает ли ведущий технические вопросы;
- как шёл прогон во времени: нагрузка, сбои, gates, расходы против бюджета;
- исправна ли машинерия: контроллер, зависшие попытки, сбои окружения,
  состояние бюджета, дрейф принятых результатов, принят ли результат только
  локально или уже есть в удалённом репозитории.

Цели:

1. **Понятно без технической подготовки.** Каждый экран сначала отвечает
   обычными словами: что происходит, что дальше, что нужно от человека.
   Технические подробности (коды, ref, gates) доступны, но не обязательны
   для понимания (§5.9).
2. **Панель показывает данные harness, а не пересказ агента.** Всё, что
   видит оператор, вычислено harness из его состояния. Ведущий агент может
   объяснить экран, но не подменяет его своим рассказом.
3. **Данные остаются в harness.** Панель рисует документ, который вычисляет
   harness, — _операторское представление_ (operator view). Своих чисел
   панель не выводит. Представление — чистая проекция состояния и политики
   со своей `viewVersion`. Простые фразы на экране — это формулировка над
   числами представления, а не новый расчёт.
4. **Один набор компонентов, два хоста.** Отдельное приложение (`npx
devcontour-harness-ui`) и DevContour рисуют одни и те же компоненты React
   по одному типу представления. DevContour кормит их из своего хранилища.
5. **Сначала только чтение.** В первом выпуске пути записи нет. Первая
   запись, позже, — ответ оператора на вопрос исполнителя с `--actor
operator` (S5, дизайн утверждает владелец).
6. **Локально и тихо.** Панель слушает только loopback. Она не делает
   исходящих запросов и не отправляет телеметрию. Секреты в представление не
   попадают.
7. **Два языка.** Русский — полноправный язык интерфейса, английский —
   запасной (с S2, §5.9, §6, §7).

Не цели: редактирование политики или графа, запуск и остановка прогонов,
удалённый или многопользовательский доступ, продуктовые функции DevContour
(продуктовая память, релизы, доски) и облачный сервис.

## 2. Архитектура

```
            harness core (devcontour-harness)                 this package
 ┌──────────────────────────────────────────────┐   ┌──────────────────────────────┐
 │ state dir + policy                           │   │ devcontour-harness-ui        │
 │   │                                          │   │                              │
 │   ▼ collectOperatorViewInput (node, git)     │   │  model/  view types, checkView│
 │   ▼ operatorView(input) ─ pure, browser-safe │──▶│  components/  React, CSS vars │
 │        │                                     │   │  app/  standalone bundle      │
 │        ├─ harness view             (stdout)  │   │  cli  loopback static server  │
 │        └─ harness serve-view  GET /view, SSE │   └──────────────┬───────────────┘
 └──────────────────────────────────────────────┘                  │ npm dependency
                                                                   ▼ (build time)
                                           DevContour web panel: same components,
                                           ViewSource adapter over its own store
```

- `operatorView` живёт в `devcontour-harness/projections`. Этот модуль уже
  безопасен для браузера (без `node:*`) и уже содержит общие проекции
  (`attemptView`, `queueStop`, `workInputOf`). Загрузчик на стороне node
  следует шаблону отчёта: `valueReport` чистый, `collectReportInput` читает
  хранилище. Предложения — в [harness-proposals.md](harness-proposals.md).
- Пакет UI никогда не импортирует внутренности harness. Он зависит только
  от схемы представления. Типы `src/model/view.ts` повторяют схему harness
  поле в поле; `tests/contract.test.ts` сверяет их с копией JSON Schema
  harness (§3).
- `devcontour-harness` — необязательная peer-зависимость. Отдельному CLI она
  нужна только для живых представлений. `--view <file>` и `--demo` работают
  без неё.
- Пакет остаётся отдельным репозиторием (решение владельца): React не
  попадает в harness.

## 3. Схема операторского представления (версия 1)

Один JSON-документ. **Схемой владеет harness** (с `0.1.0-alpha.55`):
Zod-договор `operatorViewSchema` и `workDetailViewSchema` в
`src/contracts/operator-view.ts`, пределы в `operator-view-limits.ts` и
сгенерированные JSON Schema `schemas/operator-view.schema.json` и
`schemas/work-detail-view.schema.json`. Версия `viewVersion: 1`
зафиксирована; добавления идут через `viewRevision` (§4).

Этот репозиторий схему не определяет, а повторяет:

- `src/model/view.ts` — типы TypeScript поле в поле по схеме harness;
- `tests/contract/harness/*.schema.json` — дословные копии JSON Schema
  harness; `tests/contract.test.ts` проверяет по ним обе фикстуры и
  настоящий документ `harness view`, а также что каждый объект типов
  перечисляет ровно поля схемы с тем же набором обязательных и тем же
  видом значения, а закрытые перечисления совпадают с `enum` схемы. С
  `DEVCONTOUR_HARNESS_DIR=<checkout harness>` тест сверяет копии с
  checkout побайтно и запускает `capabilities` и `view` этого checkout;
- правила, которых JSON Schema не выражает (например, `how: executed`
  требует `by` и `attempt`), проверяются в том же тесте на фикстурах.

Источник истины — договор harness. Если тип панели или копия схемы
расходится с ним, их приводят к договору harness (копию — только из
выпущенного harness). Изменение самого договора — предложение для harness
([harness-proposals.md](harness-proposals.md)), а не правка типа в панели.

Тексты простыми словами (`plain`, `line`, `reason`, сообщения
`health.warnings`) harness пишет на запрошенном языке (`harness view --lang
ru|en`). Коды, id и команды не переводятся; детали из внешнего вывода
(например, сообщение lint) остаются как есть.

```
OperatorView {
  viewVersion: 1            // major; breaking change = new number
  viewRevision: int         // additive changes inside the major
  generatedAt: ISO          // projection clock (injected in tests)
  source { producer, producerVersion, stateVersion, token }
  settings, works[], reviews[], questions[], escalations[], drift[],
  progress, history, health, activity[]?, decisions[]?, truncated?
}
```

Поля, помеченные ниже «alpha.55», harness выдаёт с `0.1.0-alpha.55`; поля
«P2» — в более поздних выпусках (номер не назначен). Источники и выпуски —
в разделе P6 [предложений](harness-proposals.md). Пока производитель поле
не выдаёт, панель пишет «нет сведений», а не ноль и не «в порядке».

### 3.1 settings

Источник — политика исполнения, привязанная к состоянию (`binding.json`),
или переданная через `--policy`. Представление несёт `policyDigest`. Если
две политики различаются, в `health.warnings` попадает
`POLICY_DIGEST_MISMATCH`.

`settings.defaulted` перечисляет пути представления через точку
(относительно `settings`, по алфавиту), значение которых взято из умолчаний
harness, а не из файла политики: например `approvalMode`,
`thresholds.repairBudget`, `thresholds.maxAttempts`, `timeouts.stall`.
Экран настроек пишет «по умолчанию» только для этих путей.

| Поле представления                                                            | Источник в harness                                                                     |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `approvalMode`                                                                | `approvalMode` (`agent` \| `operator`, по умолчанию `agent`)                           |
| `mode`, `concurrency`                                                         | `mode`, `concurrency` (1–4, по умолчанию 2)                                            |
| `roles[] {role, writer, repositoryId?}`                                       | `roles.<id>.writer`, переопределяется по репозиторию в `repositories[].roles`          |
| `reviews[] {kind, scope, repositoryId?, role?, reviewer, alternates, vendor}` | действующее `ReviewRule` для каждой области (см. ниже)                                 |
| `thresholds.inputSeverity`                                                    | `inputPolicy.threshold` (1–11, по умолчанию 7; 11 = автономно)                         |
| `thresholds.leadAnswersMaxSeverity`                                           | `inputPolicy.leadAnswers.maxSeverity` (alpha.54; отсутствие значит «ни одного»)        |
| `thresholds.leadAnswersTechnical`                                             | `inputPolicy.leadAnswers.technical` (alpha.55; отсутствие значит «нет»)                |
| `thresholds.criticalPaths`                                                    | `inputPolicy.criticalPaths.length`: только число, не пути                              |
| `thresholds.maxAttempts / repairBudget`                                       | `maxAttempts` (по умолчанию 3), `repairBudget` (по умолчанию 6)                        |
| `thresholds.maxNeutralFailures`                                               | `MAX_NEUTRAL_FAILURES`                                                                 |
| `thresholds.reviewRoundCap`                                                   | `reviewRoundCap(policy)` (сейчас `maxAttempts * 2`)                                    |
| `thresholds.reviewEscalationRounds`                                           | `REVIEW_ESCALATION_ROUNDS` (3)                                                         |
| `budgets[] {scope, usd?, timeMs?}`                                            | `budgets.work / group / total`                                                         |
| `budgetOnUnknown`                                                             | `budgets.onUnknown`                                                                    |
| `timeouts {runTimeoutMs, leaseMs, gateTimeoutFloorMs?, stall}`                | те же поля политики; `stallSweep` или `DEFAULT_STALL_SWEEP`, если его нет              |
| `lean.state`                                                                  | `on`, если `profile.layers` манифеста проекта содержит `lean`; `unknown` без манифеста |

У правил ревью есть области:

- Правила плана и договора глобальные.
- Ревью кода разрешается по цепочке роль → репозиторий → глобально, как
  `codeReview()` в harness. Поэтому `reviews[]` содержит одно глобальное
  правило `code` и по записи на каждый репозиторий или роль, которые его
  переопределяют (`scope`, `repositoryId`, `role`).
- Экран настроек показывает действующего reviewer для каждой пары роли и
  репозитория и откуда он взят.

Команды gates, `writePaths`, промпты, профили инструментов и цены в
представление не входят.

### 3.2 works[]

Одна запись на поручение, в том порядке, в каком их перечисляет `status`.
Предел: 500. Счётчики обзора берутся из `progress`, а не из этого списка
(§3.6).

| Поле                                                  | Источник в harness                                                                                                                                                                |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id, graphId, status, resultSha?`                     | `status.works[]`                                                                                                                                                                  |
| `title?`                                              | заголовок узла графа, замаскирован и обрезан до 120 символов (§9); убирается с `--no-titles`                                                                                      |
| `stage {name, step?, since?, next[], needs?}`         | `status.works[].stage` (alpha.54: `queued, blocked, prepare, writer, gates, review, integration, input, stopped, done, cancelled`)                                                |
| `stage.typical? {p50Ms, p90Ms, samples}`              | P2: наблюдаемая длительность этого этапа в этом состоянии; нет, пока образцов меньше минимума (предложено 5, §11)                                                                 |
| `attempts.used / max / left`                          | `attemptSummaryView()`: учтённые `work.attempt` против `maxAttempts`                                                                                                              |
| `attempts.failed`                                     | `attemptSummaryOf()`: учтённые сбои; прерывания при остановке не считаются                                                                                                        |
| `attempts.interrupted`                                | попытки с `interruptedByShutdown`; попытку они не расходуют                                                                                                                       |
| `attempts.rechecks`                                   | записи доказательств с `recheck: true` по всем попыткам работы                                                                                                                    |
| `attempts.neutral {used, max}`                        | `work.neutralFailures` против `MAX_NEUTRAL_FAILURES`                                                                                                                              |
| `attempts.line`                                       | `attemptSummaryLine`                                                                                                                                                              |
| `attempts.lastFailure? {attempt, bucket, plain, at?}` | alpha.55: почему остановилась прошлая попытка; `bucket` из `failureBucketOf`, `plain` — шаблон и маскированная деталь, до 160 символов                                            |
| `liveness?`                                           | `status.works[].liveness` (`quiet`, `stalled`; `active`, когда работа движется)                                                                                                   |
| `runtime?, model?`                                    | активная попытка                                                                                                                                                                  |
| `blockers[] {code, plain?, actor}`                    | alpha.55: коды `engine.blockers` с понятным текстом и тем, кто должен действовать (`null` — никто, работа ждёт очереди)                                                           |
| `dependsOn?`                                          | P2: зависимости узла в графе, для полосы плана (§5.1)                                                                                                                             |
| `target? {repositoryId, ref, acceptedSha?, remote}`   | P2: принято локально; `remote.state` (`pushed`, `not-pushed`, `unknown`) по локальной remote-tracking ref, без fetch; с ревизии 2 ещё `remote.checkedAt?` и `remote.line?` (§3.9) |
| `question?`                                           | `status.works[].input` (`requestId, state, severity`)                                                                                                                             |
| `spend {calls, usd: Bounded, durationMs}`             | `stage.spend`: собственные записи вызовов работы, по правилам стоимости отчёта (§3.7)                                                                                             |

`blockers[]` в черновике был массивом строк; объекты заменяют его до
фиксации версии 1. Это единственное обязательное поле среди новых:
пустой массив значит «ничего не мешает», поэтому производитель, который
причин не знает, всё равно выдаёт коды, а `plain` опускает. `dependsOn` —
не больше 50 id.

`Bounded = {value, bound: exact | lower | unknown}` сохраняет правило
отчёта:

- неизвестная цена показывается как «неизвестно»;
- частичная сумма показывается как `≥ $x`;
- ни то ни другое никогда не показывается как ноль.

Строк по попыткам в этом документе нет; они в документе деталей работы
(§3.11).

### 3.3 reviews[]

Одна запись на предмет ревью: план и договор (alpha.54
`reviewSubjectSummary`) и код (записи alpha.54 `review-code`). Пределы: 50
предметов и 50 замечаний на предмет.

- `kind, subject, workId?, approved`
- `rounds {used, max}`: `max` равен `null`, если у предмета нет предела.
- `open {blocking, notes}` и `accepted`: замечания, принятые как
  ограничения.
- `reviewer`, `sameVendor`: фактически использованная привязка reviewer.
- `spend {calls, usd}`
- `findings[] {id, severity, status, rounds?, disposition?, title?}`:
  - `status` — одно из `open`, `closed`, `withdrawn` или
    `accepted-limitation`.
  - `disposition` — `{decision: accepted-limitation | continue, by: lead | operator, round}`.
    Текст причины не включается.
  - `title` — текст замечания, замаскированный и затем обрезанный до 120
    символов (§9).
- `escalation? {requestId, findings[], answered}`: открытое блокирующее
  замечание, которое прошло `reviewEscalationRounds`. Решает его только
  оператор.
- `line`: однострочная сводка harness.

### 3.4 questions[] и escalations[]

`questions[]` перечисляет вопросы исполнителя (`kind: question`) во всех
открытых состояниях ввода harness (`inputStates`):

- `awaiting-answer`
- `answered-not-applied`
- `applied-awaiting-claim`
- `delivered`
- `carry-stale`

Ответа ждёт только `awaiting-answer`. Остальные состояния панель описывает
через того, кто действует следующим:

- `answered-not-applied`: ответ применяет ведущий или контроллер.
- `applied-awaiting-claim`: ответ ждёт следующей попытки.
- `delivered`: никому ничего делать не нужно.
- `carry-stale`: ведущий переносит ответ заново или отзывает его.

У каждой записи есть `requestId, workId, state, version, severity,
createdAt`, а также:

- `answerableBy`: `operator-or-lead` только когда задан `leadAnswers` и
  `severity ≤ leadAnswersMaxSeverity` — то же правило, что `leadMayAnswer`.
  С alpha.55 также для вопроса с `impact: technical`, если включён
  `leadAnswers.technical`. Иначе `operator`. Читатель, увидевший любое
  другое значение, считает его `operator`.
  `impact` сильнее правила по severity: вопрос, который не помечен явно
  `technical`, остаётся за оператором при любой severity. Панель пишет «вы
  или ведущий» только при `answerableBy: operator-or-lead` **и**
  `impact: technical`.
- `impact?` (alpha.55): `user-visible` — ответ меняет результат для
  пользователя, `technical` — не меняет. Отсутствующее или неизвестное
  значение читается как `user-visible`: отвечает только оператор.
- `plain?` (alpha.55): одна строка обычными словами — что изменится для
  пользователя. Замаскирована, обрезана до 200 символов.
- `answeredBy?`: alpha.54 `input.answeredBy`.
- `answerBasis? {by, rule?, reason?, impact, at, line}` (ревизия 1,
  alpha.56): основание последнего ответа — кто ответил (`operator`, `lead`,
  `host`), правило ведущего (`technical` | `severity`, у оператора и хоста
  правила нет), причина ведущего (маскирована, до 200 символов, нет с
  `--no-titles`), влияние вопроса, время и готовая строка `line` на языке
  представления («ответил ведущий (технический вопрос): <причина>»). Панель
  показывает «HH:MM — <line>» под состоянием вопроса и раскрытие «кто и
  почему ответил»; сама строку не составляет. Без `answerBasis` (alpha.55)
  остаётся «ответил: <кто>» по `answeredBy`, а без обоих полей о том, кто
  ответил, ничего не сказано. Детали работы alpha.56 показывают и вопросы
  закрытой работы; у отменённой или заменённой работы состояние вопроса —
  `cancelled` или `superseded` («Вопрос снят», «Вопрос заменён»).
- `title?`: текст вопроса, замаскированный и затем обрезанный до 200
  символов. Варианты и вложения не включаются. Полный текст доступен через
  `harness input-show` до S5, когда его отдаёт аутентифицированный маршрут
  деталей (§9).

У существующего `RequestLike` нет ни `workId`, ни текста вопроса, ни того,
кто ответил. Поэтому загрузчик на node передаёт очищенные сводки вопросов
(`OperatorQuestionInput` в предложении P1). Чистая проекция сырые запросы не
читает.

`escalations[]` перечисляет всё остальное, что ждёт человека или ведущего.
Каждая запись — `{workId?, subject?, code, actor, action, since}`:

- остановки, диагноз `explain` которых называет `actor: operator | lead`;
- эскалации ревью;
- пауза очереди оператором или бюджетом.

Предел: 50. Панель показывает исполнителя и действие и никогда не выполняет
их сама.

### 3.5 drift[]

Принятые результаты, целевая ref которых сдвинулась после приёмки. Источник
— alpha.54 `acceptedTargetSchema`:

- `workId, repositoryId, ref, acceptedSha, head?`
- `commitsSinceAccepted?, filesSinceAccepted?, diverged?`
- `unavailable?`: причина, если git прочитать не удалось. Замаскирована и
  обрезана.

Дрейф требует git, поэтому его вычисляет загрузчик на node и передаёт
дальше; чистая проекция только копирует. В `serve-view` дрейф кэшируется по
голове цели и пересчитывается не чаще раза в 30 с (решение владельца); тот
же кэш служит состоянию удалённого репозитория (`works[].target.remote`).
Список содержит только строки с коммитами после приёмки, расхождением или
`unavailable`. Предел: 50. Итоги по всем принятым работам — в
`health.drift`.

### 3.6 progress

Все счётчики считаются по всем поручениям состояния, а не по обрезанному
списку `works`:

- `total`, `done`, `waitingOperator`
- `byStage: Record<stage, count>`
- `running`: работы на этапе, занимающем слот (prepare, writer, gates,
  review, integration).

`queue {paused, reason?, detail?, actor?, action?}` берётся из `queueStop`
и `queuePause`, как в `status --detail`. `queue.detail` — свободный текст из
ошибок попыток, поэтому он маскируется и обрезается, как заголовок (§9). С
`--no-titles` он убирается.

### 3.7 history

Ряды для графиков. У каждого ряда одно значение на интервал; `from`, `to` и
`bucketMs` заданы явно. Окно по умолчанию — 24 ч интервалами по 15 минут (96
значений); 7 дней — по запросу (решение владельца). Загрузчик принимает и
другие окна в пределах: до 7 дней и до 500 интервалов.

| Ряд                          | Единица и правило                                                                                                                                                                                                                  |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `load`                       | Пиковое число одновременных попыток в интервале, по `startedAt` / `finishedAt`.                                                                                                                                                    |
| `attemptsStarted`            | Попытки, взятые в работу в интервале.                                                                                                                                                                                              |
| `attemptsFailed`             | Попытки, завершившиеся `failed` или `expired` в интервале. Прерывания при остановке не считаются (правило отчёта).                                                                                                                 |
| `gatesPassed`, `gatesFailed` | Применимые результаты `attempt.gate` в интервале, включая перепроверки. Пропущенный или неприменимый gate не входит ни в один ряд.                                                                                                 |
| `gatesReused`                | Gates интеграции, закрытые повторно использованным доказательством кандидата. Считаются только здесь, не как пройденные.                                                                                                           |
| `spendUsd`                   | Стоимость вызовов, завершённых в интервале, которую отчёт считает известной.                                                                                                                                                       |
| `spendBound`                 | `exact`, только если ни у одного вызова в окне нет неизвестной стоимости по правилам отчёта. Эти правила учитывают исход вызова, источник стоимости, полноту usage и попытки без записей вызовов (`callsRecorded`). Иначе `lower`. |
| `spendOpeningUsd`            | Расходы до `from`, как `Bounded`. Накопительная кривая начинается с этого значения, поэтому ранние расходы не теряются.                                                                                                            |
| `budgetUsd?`                 | Бюджет `total`, рисуется линией «расходы против бюджета».                                                                                                                                                                          |

Попытки в час на экране истории суммируются из этих интервалов в UI.
Перегруппировка интервалов — работа отображения, а не вывод новых данных.

`history.totals` (ревизия 1, alpha.56; предложение P7) — итоги окна,
посчитанные harness теми же правилами, что ряды: `attemptsStarted`,
`attemptsFailed`, `failuresByBucket` (сумма равна `attemptsFailed`),
`gatesPassed`, `gatesFailed`, `gatesReused`, `reviewRounds {plan, contract,
code, attempt}`, `spendUsd` (`Bounded`), `wallMs` (время окна, когда шла
хотя бы одна попытка), `attemptMs` (сумма времени попыток) и `loadPeak`.
Экран истории показывает их панелью «Итоги окна», и текстовые сводки
графиков берут числа оттуда. Без итогов (alpha.55) панель говорит, что в
этой версии harness их нет, — нулей вместо отсутствующих чисел нет; сводки
тогда, как и раньше, складывают ряды на экране (отображение, а не новые
данные).

### 3.8 health

- `controller {present, leaseUntil?}`: из `controller()` и часов аренды.
- `stalledAttempts`, `quietAttempts`: из живости попыток.
- `environmentFailures`: попытки в окне истории, у которых группа сбоя —
  `environment`.
- `budgeting`: `off`, когда `budgetOverview` ничего не возвращает, то есть
  в политике нет бюджетов.
- `budgets[] {scope, id?, state, spentUsd, limitUsd?, spentMs?, limitMs?}`:
  строка на каждый экземпляр области с бюджетом (total, каждая группа,
  каждая работа), из `budgetOverview`. Обзор показывает худшее состояние.
  Превышенный бюджет работы при общем в пределах показывается как
  превышенный.
- `spentTotalUsd`: все известные расходы состояния, независимо от
  бюджетов.
- `drift {checked, drifted, unavailable}`: счётчики по всем принятым
  работам. `unavailable` показывается как «не проверено», никогда как
  нулевой дрейф.
- `warnings[] {code, message}`, например `POLICY_DIGEST_MISMATCH`,
  `VIEW_TRUNCATED`, `DRIFT_UNAVAILABLE` или `STATE_NEWER_THAN_HARNESS`.
  Сообщения — фиксированные шаблоны с замаскированными значениями. Предел: 20.

### 3.9 activity[] и decisions[] (P2)

`activity[] {at, actor, action, workId?, subject?, plain}` — кто что делал
(ревизия 2, harness `0.1.0-alpha.57`). Источник — записи, которые
представление уже читает: попытки с их проверками и ревью, раунды ревью
плана, контракта и кода, вопросы исполнителя и ответы. Новые сверху, не
больше 50, окно — то же, что у истории (по умолчанию 24 ч, `--window 7d` —
7 дней); опущенные в окне — `truncated.activity`.

- `actor` — кто действовал: `controller` (запустил попытку или проверку,
  принял работу, эскалировал), `writer` (задал вопрос), `reviewer` (вердикт
  раунда), `lead`, `operator` или `host` (ответил на вопрос). Схема держит
  строку открытой: неизвестный исполнитель показывается как есть.
- `action` — код события: `attempt.started|failed|cancelled|expired|interrupted`,
  `work.accepted`, `gate.passed|failed|recheck|reused|not-launched`,
  `review.approved|changes-requested|escalated`, `question.asked|answered`.
  Неизвестный код показывается как есть.
- `plain` — фраза harness на языке `--lang`, замаскирована и обрезана
  (200). Панель её не пересказывает и не составляет.

**Нет поля — производитель не ведёт ленту** (harness alpha.55 и alpha.56):
экран пишет «harness этой версии не ведёт ленту». **Пустой список — в окне
ничего не происходило**: «за окно (24 ч) ничего не происходило». Пустое
представление без состояния выдаёт `[]`. Вынести ли ленту в отдельный
документ — открытое решение (§11).

`works[].target.remote` с ревизии 2 (alpha.57) несёт настоящее состояние:
`pushed` — принятый коммит в истории удалённой ветки, `not-pushed` — ещё
нет, `unknown` — удалённой ветки нет или git её не прочитал (с `reason`).
`checkedAt?` — когда git на этой машине последний раз обновил копию
удалённой ветки (reflog; без reflog поля нет). `line?` — готовая строка на
языке представления: «уже в удалённой ветке origin/main», «принято
локально; в удалённой ветке origin/main ещё нет», «неизвестно (нет
удалённой ветки)». Harness читает только локальные ref, config и reflog —
без `git fetch` и без сети, поэтому состояние может отставать до
следующего `fetch` или `push` на этой машине. До alpha.57 состояние всегда
`unknown` с причиной.

`decisions[] {id, kind, by, at, workId?, subject?, findingId?, requestId?,
temporary, revisit?, title?, reason?}` — решения, принятые по ходу работы:
замечание принято как ограничение, ведущий ответил на технический вопрос,
решение продолжать. `temporary: true` с условием `revisit` (из
`accept-limitation --revisit`) — временное решение, к которому нужно
вернуться. Тексты замаскированы и обрезаны. Предел: 50.

Обязательные сочетания (проверяет схема P1):

- `temporary: true` требует `revisit`;
- `kind: technical-answer` требует `requestId` и `reason`;
- `kind: accepted-limitation` требует `findingId`.

Если производитель старше схемы и поля нет, панель пишет у решения «условие
пересмотра неизвестно» или «причина не записана», а не пропускает строку.

### 3.10 Пределы, размер и токен изменений

**Размер.** У каждого списка есть предел:

| Список                    | Предел |
| ------------------------- | ------ |
| `works`                   | 500    |
| `reviews`                 | 50     |
| замечания, на предмет     | 50     |
| `questions`               | 50     |
| `escalations`             | 50     |
| `drift`                   | 50     |
| `activity`                | 50     |
| `decisions`               | 50     |
| `settings.roles`          | 100    |
| `settings.reviews`        | 100    |
| `settings.budgets`        | 3      |
| `warnings`                | 20     |
| интервалы истории         | 500    |
| `verification`, на работу | 50     |

Каждая свободная строка маскируется, затем обрезается (§9) до предела
поля:

| Строка                                                | Предел, символов |
| ----------------------------------------------------- | ---------------- |
| `works[].title`, `findings[].title`                   | 120              |
| `questions[].title`, `questions[].plain`              | 200              |
| `attempts.lastFailure.plain`, `blockers[].plain`      | 160              |
| `activity[].plain`                                    | 200              |
| `decisions[].title`, `decisions[].revisit`            | 200              |
| `decisions[].reason`                                  | 400              |
| `target.remote.reason`, `target.remote.line`          | 200              |
| `drift[].unavailable`                                 | 200              |
| `progress.queue.detail`, `warnings[].message`, `line` | 200              |

Строки настроек — имена моделей, id и перечисления. Id следуют схемам
графа и политики, которые ограничивают их длину; `verification[].gate` и
`by` — id gate, предмета ревью и среды выполнения, а не свободный текст.

С этими пределами наибольший возможный документ вычислим, но он больше
256 КБ: одни 50 предметов ревью по 50 замечаний с заголовками по 120
символов дают около 460 КБ. Поэтому байтовый предел — отдельная граница,
а не следствие пределов списков. Тест строит документ со всеми списками до
предела и строками максимальной длины и проверяет детерминированный отказ
`VIEW_TOO_LARGE`. Второй тест строит документ типичного размера (500 работ
без заголовков, остальные списки до предела) и проверяет, что он не больше
256 КБ. Согласовать пределы списков с байтовым пределом — открытое решение
(§11).

- Когда список превышает предел, проекция детерминированно его обрезает
  (оставляет первые записи в порядке harness), а `truncated` считает
  выброшенные записи по каждому списку.
- Если документ всё равно превысил бы предел, проекция отказывает с
  `VIEW_TOO_LARGE` (exit 4). Частичный документ она не возвращает.

**Детерминизм.** Для одного и того же состояния, политики, часов и опций
результат — одни и те же байты: ключи отсортированы, Map не используются.

**Токен изменений.** `source.token` выводится из содержимого. Это SHA-256
канонических байтов представления без `generatedAt` и `source.token`.

- Счётчик хранилища `ExecutionView.dataVersion()` — только подсказка серверу
  об инвалидации. Истечение аренды, живость, дрейф git, файлы политики и
  границы окна меняют представление без записи в хранилище.
- Сервер пересчитывает по подсказке и не реже раза в 5 с, пока хоть одна
  работа жива.
- `ETag` и события SSE используют содержательный токен, поэтому равные
  токены действительно означают равное представление.

### 3.11 Документ деталей работы

`harness view --work <id>` (маршрут `/api/work/<id>`, он же `/api/view?work=<id>`) возвращает
`WorkDetailView`. У него те же `viewVersion` и `viewRevision`, что у
документа обзора, и в нём есть:

- `work`: тот же `WorkView`.
- `attempts[]`: новые сверху, не больше 20. В каждой строке:
  - `attempt, status, failureBucket?, interrupted?`
  - `runtime, model?, startedAt, finishedAt?`
  - `stages[] {stage, durationMs?, outcome?}`
- `verification[]` (alpha.55): как проверялась работа, по строке на gate и
  на ревью — `{gate, kind: gate | review, phase?, result, how, by?, attempt?,
at?}`.
  - `phase`: `candidate` или `integration` — фаза записи доказательства
    gate; у строк ревью её нет.
  - `result`: `passed`, `failed`, `reused`, `skipped` (gate не применим),
    `not-run` (применим, но не запускался).
  - `by`: `harness` у выполненного gate; runtime reviewer у строки ревью;
    у прочих строк нет.
  - `how`: `executed` — запущено в этой попытке; `reused` — взято прежнее
    доказательство; `read` — reviewer прочитал diff и ничего не запускал;
    `not-checked` — не проверялось.
  - `how: executed` требует `by` и `attempt`; `how: reused` требует
    `attempt`. `attempt` — попытка проверки, к которой относится вся
    таблица (`verification.runId`), одна для всех строк; из какой попытки
    взято переиспользованное доказательство, harness не сообщает (если это
    понадобится — отдельное поле, предложение для harness). Строки ревью
    никогда не бывают `executed`.
  - Gate, который сейчас выполняется, имеет `result: not-run` и
    `how: not-checked`, пока не завершится; значения «идёт» в словаре нет.
  - Отсутствие `verification` значит «нет сведений о проверках», а не
    «проверено». Предел: 50.
- `reviews[]`, `questions[]` и `drift?` этой работы.

Строки по попыткам и проверкам живут только в этом документе и не
раздувают обзор.

### 3.12 Ревизия 4 (harness 0.1.0-alpha.60)

Все поля необязательны; договор — раздел OperatorView «Ревизия 4» в
`docs/contracts.md` harness. Панель их проверяет гейтом (`checkView`) и
показывает так:

| Поле                                        | Где                                                                                                |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `forecast {progress, time, assumptions}`    | два круга «До релиза» и «Время» наверху «Обзора» (§5.1)                                            |
| `scope {total?, tasks[]}`                   | «Ещё не переданы в harness» в «Обзоре» и «Задачах»                                                 |
| `sourceQuestions[]`                         | «Нужно от вас», вид «вопрос в трекере», со ссылкой                                                 |
| `health.sources[]`                          | «Здоровье → Источники задач»: строка совместимости                                                 |
| `updates`                                   | полоса «Доступна … — что нового · как обновить» над экраном; режим — в «Настройках», только чтение |
| `progress.queue.runner/restartBy/line`      | «Очередь стоит» и её слова (§5.1)                                                                  |
| `progress.queue.neverRun`, `scopeReason`    | «Ещё не запускали»; почему нет среза прогона (ниже)                                                |
| `works[].blockers[].step`                   | порядок «Сначала ведущий… Затем — вы» (§5.1)                                                       |
| `works[].attempts.lastFailure.kind/counted` | остановка ведущего и «попытка (не) засчитана» (§5.3)                                               |
| `works[].question.line`, `questions[].line` | где применённый ответ                                                                              |
| `questions[].options/rationale`             | вопрос целиком (§5.1)                                                                              |
| этап `plan-review`                          | «Ревью плана», ход harness                                                                         |

Поля harness `0.1.0-alpha.62` (та же ревизия 4, добавлены аддитивно;
панель `0.1.0-alpha.6`):

- `progress.queue.neverRun` — с этим каталогом ещё ничего не запускали:
  значок «Ещё не запускали» (нейтральный, не «Очередь идёт» и не «Очередь
  стоит») и строка harness `queue.line` («Ещё ничего не запускали — ведущий
  начнёт с harness run.»); в «Проблемах по ходу» ничего. Пауза важнее.
  Документ без поля (alpha.60/61) с предупреждением `STATE_NOT_FOUND`, без
  работ и без `runner` читается так же, строка — словами панели.
- `scopeReason` — почему нет `scope`: `no-snapshot` — «harness ещё не читал
  задачи из трекера»; `unreadable` — «снимок задач трекера есть, но harness
  не смог его прочитать»; неизвестное значение — «среза задач прогона в
  представлении нет (<значение>)». `scope` без задач (трекер прочитан до
  первого запуска) — «в срезе задач трекера задач нет». Пустое состояние
  прежней версии (без поля) — нейтрально «среза задач прогона в
  представлении нет»: прочитан ли трекер, по нему не сказать (прежний
  harness молча пропускал нечитаемую базу коннектора). Только документ без
  поля, в котором что-то уже запускали, говорит «эта версия harness не
  сообщает остальные задачи прогона». Опущенный по размеру срез
  (`truncated.scope`) — по-прежнему «не поместился в представление».

Неизвестные значения: `runner` без поля — прежняя догадка панели;
`basis` вне `scope`/`works` — «основа подсчёта: …» как есть; неизвестный
`level` и `mode` — как есть; полоса обновлений — только при `available` и
`needs-decision`.

### 3.13 Ревизия 5 (harness 0.1.0-alpha.65)

Все поля необязательные; документ ревизии 4 (без них) показывается, как
раньше. Панель ничего не пересчитывает: проценты, сроки и строки — поля
harness.

- **Документ настройки** (`schemas/setup-view.schema.json`): `harness view
--repository <корень>` до настройки отдаёт `{viewVersion, viewRevision,
generatedAt, source, stage {name: setup, lines}, setup {waitingFor:
project | policy}}` — без работ, здоровья и прогноза. Шлюз `checkOverview`
  отличает его от обзора (`setup` есть, `works` нет) и проверяет поля;
  `/api/view` отдаёт его с кодом 200. Страница показывает экран «Идёт
  настройка harness» со строками harness («Задач пока нет») и тем, чего
  ждёт панель (`project` — `.harness/project.json`, `policy` — политика или
  привязанное состояние). Это не ошибка: ни отказа, ни предупреждения о
  связи. Страница продолжает читать представление и сама переходит к
  экранам, когда приходит обзор. Любой экран, которому хост передал
  документ без списков обзора, показывает тот же экран, а не падает
  (`hasOverview`).
- **`stage {name, lines}`** у обзора: `setup` — состояние без работ; над
  экраном — строки harness («Идёт настройка harness», «Задач пока нет»)
  вместо прежней заметки о пустом состоянии. `work` — ничего.
- **`--repository <dir>`**: CLI передаёт harness `view --repository
  <dir>`; harness сам находит состояние и политику в `.harness/project.json`
  при каждом запуске. Подпись изменений — `.harness/`, `project.json`,
  `policy.json` и каталог состояния из manifest (`binding.json`,
  `state.sqlite`, `-wal`), перечитывается каждую секунду. Поддержку панель
  узнаёт по `repository` во входной схеме операции `view` в `capabilities`,
  а если его там нет — по ветке документа настройки в её `outputSchema`;
  harness без обоих — отказ `HARNESS_VIEW_UNAVAILABLE` с подсказкой про
  `--state`. `--check --repository` до настройки — совместимо, `view.setup: "project"`. Любой другой отказ `harness view --repository`
  (например, `POLICY_REQUIRED`) — несовместимо, выход 3; на странице такой
  отказ — отказ, не настройка. Маршрут деталей работы до настройки тоже
  отдаёт документ настройки (`checkWork`).
- **`forecast.progress`** — весь выпуск: процент включает уже принятые
  задачи и не падает, когда начинается следующая. `added[]` — «Добавлено в
  выпуск после начала: добавлена задача WEB-3 (задач 2 → 3)»; `works[]` —
  «Готовность незаконченных работ»: строка harness и полоса `percent`
  (`truncated.forecastWorks` — «ещё N не показано»).
- **`forecast.time`**: `estimate: rough` и `rough` — «осталось грубо, ~X–Y
  (по N попыткам)», подпись «грубо» в круге и пояснение; `precise` —
  прежний `remaining`; `unknown` — «неизвестно» (только тогда, даже рядом
  со старым диапазоном); `nothing` или `finishedAt` — полный круг, «выпуск
  закончен HH:MM · занял …»; прошедшее время перестаёт идти по часам
  страницы только при `finishedAt`. Без `estimate` (ревизия 4) — прежнее чтение `remaining`.
- **`works[].attempts.runs`** (только когда отличается от `used`) — «(запусков
  3, засчитано попыток 2)» рядом с попытками на «Задачах», в деталях работы и на «Обзоре» без строки harness.
- На «Обзоре» строка «принято N из M» берёт числа `forecast.progress`, когда
  он есть, — те же, что круг «До релиза»; законченный выпуск
  (`forecast.progress.left: 0`) не называется «Очередь стоит».
- **`sourceReviews[]`** и эскалации `SOURCE_REVIEW` — пункт «проверка в
  трекере» в «Нужно от вас» со строкой harness («ждут вашей проверки в
  Relay: WEB-1, WEB-2») и задачами с колонкой; число входит в заголовок
  блока и в фразу «От вас: … проверить N задач в источнике задач». Решением
  такая эскалация не считается; эскалация, которой нет в списке (усечение,
  `truncated.sourceReviews`), — отдельный пункт.

### 3.14 Ревизия 6 (harness 0.1.0-alpha.66)

Все поля необязательные; документ ревизии 5 (без них) показывается, как
раньше (`asAlpha65` в тестах). Панель ничего не пересчитывает: цифры,
строки и подписи шагов — поля harness; панель выбирает только цвет и слово
для состояния, которое назвал harness.

- **`lead`** — сессия ведущего (`active`, `since`, `until`, `endedAt`),
  последняя заметка и журнал новыми сверху (`notes[]`: заметки и команды
  harness ведущего). «Журнал → Ведущий» (`#/lead`): сессия, строка harness,
  выпуск (`forecast.progress.release`: состояние, время и итоговый отчёт),
  журнал со ссылками на работы (код действия — в «подробностях») и ссылка
  на ленту «Кто что делал» с фильтром по ведущему; `truncated.leadNotes` —
  «ещё N записей не показаны». На «Обзоре» — короткая панель: работает ли,
  с какого времени, последняя заметка и состояние выпуска. Без `lead` в
  ревизии 6 — «ведущий ещё не начинал»; до неё — «передаёт harness alpha.66».
- **Прогноз**: `progress.approved` и `progress.percent` — две цифры («по
  утверждённому плану ~27 %», «с планируемыми задачами ~23 %») и строка
  `planned.line`; `release` — состояние словами («код в работе», «код
  принят, ведущий работает», «выпуск готов»), подпись в круге «код принят»;
  `lead` — «доля ведущего: X из 10 %» и шаги (план, вопросы, передача в
  трекер, отчёт) с отметкой; `time.chain` — «цепочка зависимостей: не
  меньше N задач подряд»; `time.lead.line`. 100 % круг показывает, только
  если так прислал harness (он даёт 100 лишь после `release done`).
- **`planned[]`** — карточки «ещё не утверждена» на «Задачах» (строка
  harness, откуда задача, после каких работ); такая задача не повторяется в
  «Ещё не переданы в harness». **`works[].planned`** — фаза «Ещё не
  утверждена» и значок на карточке, в плане «Обзора» и в деталях.
- **`resources`** — «Что задействовано» на «Обзоре»: строки `lines` и под
  «подробнее» роли, изоляция, инструменты, хранилище зависимостей, службы
  (docker и lifecycle: работает, остановлено, осталось после попыток) и
  проверки. Раздел, опущенный по размеру (`truncated.resources`), назван.
- **`previews[]`** — «Посмотреть результат»: ссылка только на адрес вида
  `http://127.0.0.1:<порт>/` из harness (новая вкладка, `noopener`), что
  показано (ref, коммит, работа), когда запущено и когда остановится само,
  и команды `harness preview-stop`/`preview-start` текстом. Кнопок нет:
  панель только читает, а записи из панели — отдельный утверждённый срез
  (§10, S5). Без `previews` в ревизии 6 — «ни одно превью не запущено» и
  команда запуска; до неё — панели нет.
- **`works[].track`** — путь работы. На карточке — одна строка сегментов:
  попытка — сегмент из шагов (код, проверки, ревью, интеграция), решения и
  «принято» — отдельные метки (решение — ромб, конец — квадрат). Цвета:
  впереди — серый, идёт сейчас — зелёный с пульсацией (без неё при
  `prefers-reduced-motion`), не прошло — красный, ждёт — янтарный,
  решение ведущего — синий, доработка — фиолетовый (пунктирная рамка
  сегмента), пропущено — пустой кружок. У каждого сегмента — текст для
  экранного диктора, всплывающая подсказка повторяет его для мыши. В деталях
  — таблица: №, попытка, шаг, состояние, время, причина, и легенда словами.
  `truncated` — «N ранних шагов не показаны». Harness alpha.66 присылает
  ещё не пройденные шаги идущей попытки как `skipped`; панель называет их
  «впереди» (серый), а не «пропущено». Без пути: до ревизии 6 — «передаёт
  harness alpha.66», в ревизии 6 (опущен по размеру) — так и сказано.
- **`settings.decisions`** — «Кто принимает решения» первым блоком
  «Настроек»: итог одной фразой (`summary` на языке панели), `warning` —
  предупреждением, каждая настройка — значение словами, откуда оно («из
  политики», «выведено из соседней настройки», «по умолчанию») и
  объяснение harness на языке панели.
- **`works[].restoredFrom: cancelled-rework`** и `restoredLine` — работа
  принята, рядом значок «доработка отменена» и строка harness.
- **Разбор ведущего**: `DIAGNOSIS_REQUIRED` (блокировка, эскалация и
  `stage.needs {lead, diagnose}`) — одна строка «Делает ведущий: разобрать
  причину повторных отказов», не «Нужно от вас»; так же исчерпанные попытки,
  когда сбрасывает ведущий (`ATTEMPTS_EXHAUSTED` с `actor: lead`).

## 4. Версии и совместимость

**Поля версий.**

- `viewVersion` — целая мажорная версия. Меняется только когда поле
  удалено, переименовано или меняет смысл.
- `viewRevision` растёт при добавлениях: новое необязательное поле, новое
  значение перечисления или новый раздел.
- Новое значение перечисления считается добавлением, только если
  запасное чтение у читателя безопасно. Если безопасного чтения нет, это
  новая мажорная версия.

**Читатели** (`checkView` в `src/model/compat.ts`, с тестами):

- UI принимает свою мажорную версию с любой ревизией и игнорирует
  неизвестные поля.
- Каждое поле, которое читает компонент, сначала проверяется. Искажённый
  документ отклоняется с `NOT_A_VIEW` и путями к ошибкам, а не падает при
  отрисовке.
- Неизвестные значения читаются осторожно:
  - неизвестный этап показывается как есть;
  - неизвестная граница стоимости — как «неизвестно»;
  - неизвестный `answerableBy` значит, что отвечает только оператор;
  - неизвестный или отсутствующий `impact` значит `user-visible`;
  - неизвестное состояние вопроса значит «посмотрите перед действием»;
  - неизвестное состояние бюджета считается `undetermined`;
  - неизвестный `how` проверки показывается как «способ неизвестен», не как
    «проверено»;
  - неизвестное `remote.state` — как «неизвестно», не как «отправлено»,
    даже если его `line` говорит иное; состояние решает только `state`, у
    `unknown` панель пишет причину (`reason`).
- Поиск идёт только по собственным свойствам, поэтому `__proto__` и похожие
  ключи показываются как текст.
- Сборка знает ревизию 4 (`KNOWN_VIEW_REVISION`, harness
  `0.1.0-alpha.60`, §3.12) и полностью рисует ревизии 3 (`0.1.0-alpha.59`), 2 (`0.1.0-alpha.57` и
  `.58`), 1 (`0.1.0-alpha.56`) и 0 (`0.1.0-alpha.55`): поля ревизий 1–3
  необязательны, и их отсутствие никогда не показывается нулём. Ревизия 3
  добавляет `unused: true` у стадий попытки (`attempts[].stages[]` деталей
  работы: хранилище зависимостей, не развернувшее seed, — «не
  используется»); с alpha.59 подготовка зависимостей — свои стадии
  `prepare` и `integration-prepare`, а не часть написания кода. Остановку
  исполнителя из-за окружения (`writer-environment`) ревизия 3 не
  называет отдельным полем; для неё панель узнаёт остановку только по
  всему, что harness alpha.59 для неё пишет: работа `stopped`,
  `stage.needs` — ведущий, `diagnose-failure`, группа сбоя `environment` и
  неизменная фраза harness «окружение закрыло исполнителю обязательный
  шаг» (§5.3). С ревизией 4 это факты `lastFailure.kind: needs-lead` и
  `counted: false` (предложение P13 закрыто), фраза больше не читается:
  документ ревизии 4 без этих полей ничего не говорит («неизвестно»), а
  данное `counted` никогда не переписывается фразой. Подвид («окружение
  исполнителя» или предпроверка) ревизия 4 не различает, поэтому панель
  его не называет и пишет фразу harness. Когда `viewRevision` новее, чем знает сборка, приложение пишет
  «данные новее панели — обновите панель, чтобы видеть всё».
- Любая другая мажорная версия отклоняется с `VIEW_VERSION_UNSUPPORTED` и
  подсказкой, как исправить. UI не угадывает.
- HTTP 409 сохраняет код и сообщение при прохождении через
  `httpViewSource`.

**Производители.** Harness держит выпущенную мажорную версию всю линию
альф `0.1.x`. Когда появляется новая мажорная, `harness view --view-version
N` оставляет предыдущую доступной ещё минимум один минорный выпуск.

**Версии пакетов.** Диапазон peer для `devcontour-harness`
(`>=0.1.0-alpha.55 <0.2.0`) — рекомендация; совместимость решает версия
представления. `devcontour-harness-ui --check` (срез S3) выполняет:

- `harness --version`
- `harness capabilities`, где должен быть `view`
- `harness view`

и печатает `{harness, ui, viewVersion, compatible, fix?}`.

**`stateVersion`** копируется как есть, чтобы панель отличала «старое
состояние, новый harness» (предупреждение) от «состояния нет» (пустое
представление).

## 5. Экраны

Верхнее меню — пять разделов: **Обзор · Задачи · Решения · Журнал ·
Настройки** (en: Overview · Tasks · Decisions · Log · Settings). Навигация —
hash-маршруты, поэтому отдельной сборке не нужна маршрутизация на сервере:
`#/` (обзор), `#/tasks` (задачи), `#/work/<id>` (процесс одной задачи,
пункт меню «Задачи»), `#/decisions`, `#/activity`, `#/history`, `#/health`
(три экрана «Журнала» со своей второй строкой: «Кто что делал · История ·
Здоровье») и `#/settings`. Старый адрес `#/reviews` ведёт на `#/tasks`:
ревью теперь этап процесса задачи (§5.3). Каждый экран работает при
ширине 390 px без горизонтальной прокрутки страницы. Таблицы ниже 640 px
превращаются в стопку карточек. Графики сохраняют `viewBox` и рисуются
встроенным SVG, без библиотек графиков. У каждого графика есть текстовая
сводка и таблица данных для экранного диктора.

Названия разделов — обычные слова. Технические названия (этапы, коды,
gates) стоят рядом мелким шрифтом или внутри «что это значит».

### 5.0 Внешний вид (alpha.4)

Владелец смотрит панель без технической подготовки; прежний вид читался
«слишком машинным». С alpha.4:

- **Карточки.** Каждый раздел — карточка (shadcn/ui: Card, Badge, Button,
  Progress, RadioGroup, Alert) на фоне страницы; статус — значок с текстом,
  цвет только повторяет слово. Компоненты shadcn/ui скопированы в
  `src/components/ui/` и опираются на примитивы Radix (Progress,
  RadioGroup, Slot).
- **Стили — Tailwind CSS 4 с префиксом `hui:`** (`hui:flex`,
  `hui:bg-card`), без preflight. Переменные темы Tailwind тоже с префиксом
  (`--hui-spacing`), цвета утилит — сами токены `--hui-*`. Сборка
  (`scripts/build-css.mjs`) переносит единственное глобальное правило
  Tailwind (запасные значения `--tw-*` для старых браузеров) внутрь
  `.hui`. `tests/styles.test.ts` собирает таблицу стилей и проверяет каждое
  правило: селектор начинается с `.hui` или `.hui-…`, либо это `:root` с
  одними переменными `--hui-*`; все слои названы `hui-*`; кроме слоёв и
  медиазапросов есть только регистрации `@property --tw-*`.
- **Тёмная тема.** По `prefers-color-scheme` и по выбору зрителя в
  «Настройках» («Как в системе · Светлая · Тёмная»). Выбор отдельного
  приложения хранится в `localStorage` этого браузера (`data-theme` на
  `<html>`); хост задаёт тему сам.
- **Новая сборка панели (F-AF).** `/api/health` называет сборку (`build` —
  хеш `index.html`), та же метка стоит в отданной странице (`<meta
name="hui-build">`), страница отдаётся с `cache-control: no-cache`.
  Открытая вкладка раз в минуту и при возвращении на неё сверяет сборку и
  при смене пишет «Панель обновилась… [Обновить страницу]».
- **Коды — только в «подробностях» (F-AA).** Коды причин, действий,
  предупреждений и событий, id запросов и полные id работ стоят в раскрытии
  «подробности», а не в основном тексте.

- **Первая строка (alpha.4)** — одно простое предложение о том, что
  происходит: над чем работает harness и на каком этапе; «Все работы
  приняты: N из N»; «Сейчас ничего не выполняется: очередь на паузе /
  работа ждёт вашего решения / harness не запущен / работы ждут своей
  очереди или ведущего». Под ней — прежняя фраза «Сейчас: … От вас: …».
- **Очередь стоит (F-X).** С ревизией 4 это решает harness:
  `progress.queue.runner: not-running` (никто не запущен) — «Очередь
  стоит» со строкой harness `queue.line` («Очередь стоит — никто не
  запущен: … (ведущий: harness run)») и тем, кто запускает
  (`restartBy`); `running` — очередь идёт, что бы ни говорило поле
  контроллера. Строка `queue.line` показывается при любом состоянии
  очереди. Идёт ревью плана (`plan-review`) — первая строка «Сейчас
  harness проводит ревью плана: …», а не «работы ждут ведущего». Догадка панели осталась только для документа без `runner`
  (ревизии 0–3): если очередь не на паузе, контроллера нет
  (`health.controller.present: false`), ничего не выполняется и есть
  непринятые работы, значок пишет «Очередь стоит» (а не «Очередь идёт») с
  тем, кто действует: «harness не запущен, и сама очередь не пойдёт —
  ведущему нужно снова запустить harness»; в «Проблемах по ходу» — та же
  строка. Считаются только работы harness: задачи вне harness передаёт
  ведущий, очередь из-за них не «стоит». Всё принято — «Всё принято» (при
  задачах вне harness — «Всё, что в harness, принято»); всё отменено и
  ничего не принято — «Всё отменено», а не «принято». Отменённые работы в
  счёте стоят отдельно («· отменено N») и отдельной частью полосы.
- **Прогноз выпуска (alpha.5, ревизия 4).** Над первой строкой — два
  больших круговых индикатора из `forecast` (harness alpha.60,
  предложение P11; формула — в договоре harness, панель ничего не
  пересчитывает):
  - «До релиза» — `forecast.progress.percent` в центре («~23 % готово»),
    под ним строка harness `progress.line` («готово ~23 %, осталось задач:
    5 из 6, в работе: 1») и основа подсчёта (`basis`: все задачи прогона
    или только работы harness);
  - «Время» — в центре остаток диапазоном («~1,5–3 ч», нижняя граница вниз,
    верхняя вверх), под ним «прошло 2 ч 50 мин · осталось ~1,5–3 ч» из
    `time.elapsedMs` и `time.remaining` и основание («по 6 закончившимся
    попыткам; попыток на принятую задачу — 1,2»). Закрашена прошедшая
    часть от «прошло + осталось» по верхней границе, светлая дуга — до
    нижней: это только геометрия круга над числами harness;
  - есть `remaining`, но нет `elapsedMs` и `startedAt` — диапазон
    остаётся («сколько прошло — неизвестно · осталось ~…»), круг не
    закрашен;
  - нет `remaining` (мало наблюдений) — круг в состоянии
    «неизвестно» (пунктир, «?» и «неизвестно» в центре, без
    `aria-valuenow`) с причиной; ничего не осталось (`left: 0`) — полный
    круг и «осталось: ничего». Неизвестное никогда не показывается нулём;
  - ожидание людей и ведущего (`time.humanWait`) — отдельной строкой «Ждут
    людей или ведущего сейчас: N, дольше всех — X. В прогноз это не
    входит»;
  - «прошло» и ожидание идут по часам зрителя от точек отсчёта harness
    (`time.startedAt`, `humanWait.since`): harness держит их в токене
    содержимого, а сами длительности — нет, поэтому открытая страница с
    неизменным документом не замирает. Меньше числа harness панель не
    пишет;
  - «что это значит» — `forecast.assumptions` словами harness, «это
    наблюдение, а не обещание» и обе строки harness, как в `status
--human`;
  - доступность: каждый круг — `role="progressbar"` с именем по
    заголовку, `aria-valuemin/max` 0–100, `aria-valuenow` (у «Времени» —
    доля закрашенного) и `aria-valuetext` с той же строкой, что видна
    рядом; SVG скрыт от диктора. Цвета — токены темы, обе темы; при 1280
    px круги рядом, при 390 px один под другим, без горизонтальной
    прокрутки;
  - без `forecast` кругов нет: у ревизий 0–3 «Весь объём работ» пишет,
    почему («эта версия harness не сообщает прогноз»), у ревизии 4 —
    «прогноза нет: harness не даёт его для этого объёма (работ нет или все
    отменены)»; в обоих случаях — прежние полоса и оценка панели (alpha.4,
    ниже). С `forecast` полоса, оценка панели и «одна попытка в среднем» у
    ждущих работ не показываются, а строка счёта называет только работы
    harness («В harness: принято 1 из 4 · …»): объём выпуска — у круга.
  - Задачи среза сверх предела (`truncated.scope`) называются «ещё N задач
    среза прогона не показано; их состояние здесь неизвестно» и не
    добавляются ни к «не переданы», ни к общему числу; срез, не
    поместившийся в документ целиком, — «срез прогона не поместился в
    представление».
- **Весь объём работ.** «Сделано N из M · в работе R · ждут W» из
  `progress` (никогда из обрезанного `works`); без прогноза — полоса из
  трёх частей с тем же числом (`role="progressbar"`, значение — принятые);
  список работ со значком состояния и примерным сроком. Задачи прогона,
  которых ещё нет в harness, — из раздела `scope` (ревизия 4, harness
  alpha.60, [предложение P10](harness-proposals.md)): «Ещё не переданы в
  harness (N)», у каждой — ключ и заголовок («DEMO-6: Печать отчёта»),
  «не передана в harness» или «ждёт готовности» и причина. Без `scope` карточка пишет, что показаны только работы, уже
  переданные в harness, и что эта версия harness остальные задачи не
  сообщает.
- **Сроки — диапазоном, по фактическому времени (без `forecast`).**
  Единственная арифметика панели над числами harness, для ревизий 0–3
  (с ревизией 4 её заменил `forecast`; остаток этапа из `stage.typical`
  остаётся):
  - осталось на этапе работающей работы: `stage.typical` (p50–p90) минус
    уже прошедшее; дольше p90 — «этап идёт дольше обычного (обычно до X)»;
  - одна попытка в среднем: `history.totals.attemptMs /
attemptsStarted`, только при 3 попытках и больше за окно;
  - осталось всего: каждой непринятой работе нужна хотя бы одна попытка
    средней длины; в лучшем случае `concurrency` идут одновременно, в
    худшем — одна за другой (`⌈N / concurrency⌉ × среднее` …
    `N × среднее`), с оговоркой «если каждой хватит одной попытки; ожидание
    ответов людей сюда не входит» и основанием («попытка в среднем длится
    50 мин, по 11 попыткам»);
  - нижняя граница округляется вниз, верхняя вверх; без наблюдений —
    «пока сказать нельзя» с причиной, никогда не ноль.
- **Проблемы по ходу** простыми словами, каждая строка — запись
  представления: последняя неудачная попытка каждой непринятой работы
  (`attempts.lastFailure`, группа сбоя словами), остановки с причиной и
  тем, кто действует, стоящая очередь, зависшие попытки, сбои окружения,
  превышенный бюджет, изменения после приёмки. Принятые и отменённые
  работы сюда не попадают.
- **Технические вопросы ведущего (F-W).** Вопрос, на который ведущий
  отвечает по политике (`leadAnswers.technical` и `leadMayAnswer`), не
  входит в «Нужно от вас» и в число «От вас»: он стоит в «Остальные
  ожидания → Делает ведущий» целиком, с пометкой «Отвечает ведущий… Вы
  тоже можете ответить».
- **Работающая работа не ждёт (F-J), принятая не стоит (F-AY).** У работы
  на этапе со слотом (`prepare`…`integration`) причины «не готова к
  запуску» и `stage.needs` вида `wait`/`none` описывают саму идущую
  попытку: они не дают строк ни в «Ждут очереди», ни в «Делает …».
  Принятые и отменённые работы не попадают в ожидания.

- **Кто действует дальше.** Разделы и фраза в шапке строятся одним чистым
  проходом `nextSteps(view)` (`src/model/steps.ts`) по `questions`,
  `escalations`, `works[].blockers` и `works[].stage.needs`. Записи об одной
  остановке сливаются в одну строку: причина и эскалация — при том же
  исполнителе и коде; `stage.needs` — с записью того же исполнителя и
  действия, иначе с причиной, код которой просит это действие
  (`ATTEMPTS_EXHAUSTED` → `reset-attempts`, `APPROVAL_STALE` →
  `review-plan`, `INPUT_REQUIRED` → `answer`/`answer-input`/`apply-input`,
  …), иначе — у работы с непринятыми зависимостями и только для действий
  `diagnose-failure`, `wait`, `none` — с ожиданием зависимости, иначе
  отдельной строкой (например, `fix-access` оператора не теряется). Один исполнитель ещё не
  значит одну остановку: разбор сбоя ведущим не сливается с согласованием
  плана. `needs` с `actor: null` ничего не просит и строки не даёт. Каждая
  строка попадает ровно в одно место:
  - вопрос в `awaiting-answer` — «Нужно от вас», вид «вопрос»;
  - действие оператора (`actor: operator`; `user` в диагнозе harness
    читается так же) — «Нужно от вас», вид «решение». Причина «ждёт ответа»
    (`INPUT_REQUIRED`, действие `answer`/`answer-input`) — это вопрос, а не
    решение: она решением не считается. Если такого вопроса в списке нет,
    раздел пишет «ждут вашего ответа, но вопрос не показан» с именами работ;
  - действие ведущего — «Остальные ожидания → Делает ведущий». Одинаковая
    причина нескольких работ одного плана (`graphId`; одно согласование) —
    одна строка со всеми работами, даже если действие названо только в
    одной из записей; у разных планов — разные строки.
    Ответ ведущего на вопрос, который сейчас ждёт ответа, — это сам вопрос,
    а не отдельная строка;
  - действие другого участника (контроллер, хост) — «Делает <кто>»;
  - причина «ждёт зависимости» (`NOT_READY`, `DEPENDENCY_*`) у работы с
    непринятыми `dependsOn` — «Ждут другой работы» с тем, кто дальше
    действует по той работе («по ней дальше действует: ведущий, затем
    вы»), каким бы ни был исполнитель самой записи. Без исполнителей по той
    работе строка говорит, что она делает: идёт этап («действует: harness —
    этап …»), сама ждёт другой работы (это сильнее этапа «в очереди»), ждёт
    очереди; работы нет в
    представлении или о ней ничего не сказано — «кто действует —
    неизвестно», а не «никто»;
  - `actor: null` и остановка без причины — «Ждут очереди». Принятые и
    отменённые работы туда не попадают.
- **Порядок.** Ревизия 4: порядок снятия задаёт harness
  (`blockers[].step`, 1 — первой). Решению оператора предшествуют шаги
  других участников той же работы с меньшим `step`, в порядке harness:
  «Сначала ведущий: …. Затем — вы.» (для сброса попыток после
  согласования плана — прежняя фраза ниже); harness поставил сброс первым
  — никакого «сначала». Список кодов панели тогда не читается, и документ
  ревизии 4 без `step` оставляет порядок неизвестным (без «сначала»). Без
  `step` в ревизиях 0–3: пока у той же работы стоит `APPROVAL_STALE` или
  `APPROVAL_REQUIRED` ведущего, harness не начинает новую попытку (проверка
  согласования идёт раньше счёта попыток), и сброс оператора ничего не
  изменит. Решение оператора тогда говорит «Сначала ведущий: …. Потом — вы»,
  а шапка — «принять 1 решение (после ведущего)», если так у всех решений.
  Другие действия ведущего (например, разбор сбоя) порядок не задают.
- **Фраза в шапке.** Первая строка — одно предложение «Сейчас: … От вас:
  …». «Сейчас» перечисляет `progress.running`, `byStage.queued`,
  `byStage.stopped` и паузу очереди; «От вас» — ровно пункты раздела «Нужно
  от вас»: вопросы и решения. Число в шапке равно числу пунктов раздела.
  Это формулировка над записями представления, а не новый расчёт. «Ничего
  не нужно» пишется только когда выполнено всё сразу:
  - в разделе нет пунктов;
  - `progress.waitingOperator` равен 0 (иначе: «N работ ждут вашего
    действия»). Раздел в этом случае тоже не пишет «ничего не нужно»: если
    harness считает больше ждущих вас работ, чем названо в разделе, там
    стоит «ещё N работ ждут вашего действия, но в этом представлении не
    показаны»;
  - `truncated.questions` и `truncated.escalations` не заданы (иначе к
    числу добавляется «и, возможно, ещё (список обрезан)», а при пустом
    списке пишется «неизвестно — список обрезан»);
  - нет вопросов в состоянии, которого сборка не знает (это тоже
    «неизвестно»; раздел тогда пишет «Неизвестно: у вопроса состояние,
    которого панель не знает»).
- **Список работ** (P2, внутри «Весь объём работ»). Работы в порядке
  `status` со значком этапа, примерным сроком и связями `dependsOn`;
  отмечено, где прогон сейчас. Если `works` обрезан,
  полоса так и пишет. Без `dependsOn` полоса показывает только порядок.
- **Имена работ.** В предложениях работа называется ключом заголовка до
  двоеточия («WEB-1: …» → «WEB-1»); без ключа — читаемым id как есть, а
  непрозрачный id harness (`t62c1…`) заменяется заголовком. Полные id — в
  «подробностях».
- **Разделы**, в этом порядке на любой ширине:
  1. «Нужно от вас (N)» — без числа, если пунктов нет («Сейчас от вас ничего
     не нужно»). Вопросы: строка `plain` («что изменится»), варианты
     ответа с пометкой «рекомендуется» и обоснование исполнителя
     (`options`, `rationale`, ревизия 4), кто может ответить. Вопросы
     владельцу из трекера задач (`sourceQuestions[]`, ревизия 4) — вид
     «вопрос в трекере»: заголовок, вопрос, варианты, рекомендация,
     временный ответ, задачи, «Отвечают в трекере задач, панель только
     показывает вопрос» со ссылкой на документ (только `http(s)`; иначе —
     ключ документа текстом) и когда связка его прочитала; они входят в
     число «Нужно от вас», «От вас» и объявление для диктора. Обрезанный
     или выброшенный по размеру список (`truncated.sourceQuestions`) так и
     назван, и шапка тогда не пишет «ничего не нужно». Вопросу, перед
     которым harness ставит шаг ведущего (`blockers[].step`), предшествует
     «Сначала ведущий: …. Затем — вы.» Вопрос показан целиком в панели (заголовок и `plain`), а
     не командой `harness input-show` (F-Y); id и версия запроса — в
     «подробностях». Решения: что сделать обычными словами («Сбросить
     попытки — WEB-1»), «Почему:» из `plain`, для сброса попыток — строка
     попыток и «попросите ведущего сбросить попытки»; команда `harness
retry … --reset --reason …` — в «подробностях»; порядок, если ведущий
     первый. Коды, исполнители и
     действия записей — в раскрытии «подробности». Кнопки, которая
     действует за оператора, нет.
  2. «Проблемы по ходу» — рядом с «Нужно от вас» (на узком экране ниже).
  3. «Сейчас в работе»: этап обычными словами, сколько длится, обычный
     диапазон `stage.typical` («обычно 5–12 мин»; без него диапазона нет),
     сколько осталось на этапе, строка попыток и «почему повтор» из
     `attempts.lastFailure`.
  4. «Остальные ожидания (N)»: подгруппы «Делает ведущий», «Делает <кто>» и
     «Ждут другой работы». Если в «Нужно от вас» есть пункты, первая строка
     отсылает к ним. У ведущего — пометка, что это действие ведущего, а не
     ваше.
  5. «Ждут очереди»: работы, где `actor: null` («просто ждёт очереди —
     ничего не нужно»), и остановки без причины («кто действует —
     неизвестно»).
  6. «Другие вопросы»: вопросы не в `awaiting-answer` — с тем, кто ответил и
     что дальше. В число «От вас» они не входят.
  7. «Принятые», карточки здоровья и подвал.

  Перед ними — первая строка и «Весь объём работ».

- **Группы отказов.** В строке попыток (`attempts.line`) ключи групп
  после «отказов N» (`incomplete`, `time-limit`, `input`, …) показываются
  словами глоссария групп («работа не доделана», «время вышло», «нужен
  ответ»); ключ, которого сборка не знает, остаётся как есть в `code`.
  Остальной текст строки — текст harness без изменений. Так же — в «Сейчас
  в работе» и в деталях работы.
- **Подвал.** «Данные harness на HH:MM; панель ничего не меняет». Время —
  `generatedAt` в часовом поясе зрителя. Если `generatedAt` приходится не
  на сегодняшний день зрителя, перед временем стоит дата `ДД.ММ.ГГГГ`.
  Неверный часовой пояс даёт «на неизвестное время», а не падение экрана.
  Гейт принимает только момент ISO 8601 с явной зоной (`Z` или `±ЧЧ:ММ`) и
  существующей датой календаря.

### 5.2 Детали работы (`#/work/<id>`)

```
┌───────────────────────────────────────────────────────────────┐
│ ← locale-format   Даты по локали          Проверки · работает │
│ Сейчас: проверки (candidate-test:unit) с 11:52, 7 мин 50 с;   │

├───────────────────────────────┴───────────────────────────────┤
│ Что проверено                                                 │
│ lint            пройдено · запущено в попытке 2 (claude)      │
│ unit            ещё не запускалось — проверки идут            │
│ код, ревью      прочитал diff, ничего не запускал (codex)     │
│ e2e             не проверялось                                │
├───────────────────────────────────────────────────────────────┤
│ Принято: ещё нет (после приёмки: локально; в удалённой ветке) │
│ Дрейф после приёмки: —                                        │
└───────────────────────────────────────────────────────────────┘
```

- Строки попыток и проверок — из документа деталей работы (§3.11).
- **Процесс (alpha.4).** Лента последней попытки: подготовка → написание
  кода → проверки → ревью → интеграция → приёмка, у каждого этапа —
  состояние («пройдено», «не прошло», «идёт сейчас», «впереди», «не
  дошло» — у прежней попытки, «в следующей попытке» — у остановленной
  последней, когда попытки остались, «не понадобилось» — у принятой работы
  без этого этапа, «итог неизвестен» — когда записи этапа нет) и время из `attempts[].stages`. Ревью — один
  из этапов; рядом с ним — раунды ревью кода из `reviews[]`. Этап новой
  версии harness, которого сборка не знает, стоит после известных под
  своим именем. Прежние попытки — в раскрытии, у каждой своя лента и группа
  сбоя. Без попыток — «Попыток ещё не было: процесс начнётся с
  подготовки». Заголовок — название работы; полный id — в «подробностях».
  Ссылка назад ведёт к задачам. Шаг ленты собирает записанные стадии
  harness (`processStageOf`, та же карта, что `stageOfStep` в harness):
  подготовка — `dependency-store`, `writer-dependencies`, `prepare`,
  `candidate-environment:setup|ready|port-shared:*`; написание —
  `implementation`, `implementation-reuse`; проверки — `candidate-test:*`,
  `candidate-consumer:*`, `candidate-recheck:*`, `generate:*`; ревью —
  `candidate-review` и уборка окружения после него
  (`candidate-environment:cleanup`); интеграция — все `integration-*`
  (в том числе `integration-prepare`). Время шага — сумма частей, кроме
  уборки окружения и ожидания очереди интеграции (`integration-wait`);
  они же не делают шаг непройденным. Проверка, которую прошёл повтор
  (`*-recheck:<gate>`), шаг не проваливает; провал, после которого попытка
  пошла дальше, читается как пройденный шаг. Пока работа на этапе, шаг
  «идёт сейчас», даже между двумя его частями. Части перечислены словами
  под шагом («хранилище зависимостей: не используется, 2 с; подготовка
  зависимостей: пройдено, 18 с»); стадия, которую сборка не знает, —
  «другой шаг harness», её id — в «подробностях».
- **«Почему повтор»** — `attempts.lastFailure.plain`, группа сбоя и номер
  попытки. Без `lastFailure` раздел пишет «причина прошлой остановки
  неизвестна», если сбои были, и не показывается, если сбоев не было.
- **«Что проверено»** — каждая строка `verification[]` говорит, что
  проверено, как (`how`) и кем (`by`). Слова «проверено» без способа нет.
  Ревью, которое читало diff, так и подписано: «прочитал diff, ничего не
  запускал». Без `verification` — «нет сведений о проверках».
- **«Принято локально / в удалённой ветке»** — из `resultSha` и `target`.
  Состояние удалённой ветки harness берёт из её копии на этой машине
  (remote-tracking ref) без fetch и без сети. У `pushed` и `not-pushed`
  панель называет состояние словами строки harness, но из самого
  `remote.state` и ветки из `trackingRef`: «Принято локально; в удалённой
  ветке origin/main ещё нет.», «Принято локально; уже в удалённой ветке
  origin/main.» Строку `remote.line` панель не цитирует: harness обрезает
  её до 200 символов, и при длинном имени ветки обрезка срезает «ещё нет» —
  отрицательное состояние читалось бы как утвердительное (предложение P9).
  Ниже — «Сверено с копией удалённой ветки на этой машине, без сети; git
  обновил копию: вчера 20:30» из `remote.checkedAt` (сегодня — только
  время, вчера — «вчера», раньше — дата); без `checkedAt` — «когда git
  обновлял копию — неизвестно». Рядом раскрытие «в удалённой ветке: что
  это значит» (§12); в обзоре — одно на список. `unknown` и незнакомое
  состояние — «неизвестно» с причиной, никогда не «нет» и не «отправлено».
  У alpha.55 и alpha.56 состояние всегда `unknown` с причиной.
- При 390 px колонки складываются так: сейчас, этапы, почему повтор,
  что проверено, расходы и что мешает, ревью, принято, дрейф. Этапы
  становятся вертикальным списком.

### 5.3 Задачи (`#/tasks`, alpha.4; вместо «Ревью»)

```
┌──────────────────────────────────────┐ ┌──────────────────────────────────────┐
│ Format dates by locale [Идёт работа] │ │ Export report as CSV  [Ждёт ответа]  │
│ Сейчас: этап «Проверки», идёт 7 мин. │ │ Сейчас: ждёт вашего ответа на вопрос.│
│ осталось на этапе: до 5 мин          │ │ одна попытка в среднем около 50 мин  │
│ Попытки: израсходовано 2 из 3,       │ │ Попытки: израсходовано 1 из 3, ост. 2│
│ осталось 1   ██████████░░░░          │ │ ██████░░░░░░░░                       │
│ Ревью кода ещё не было               │ │ Ревью кода ещё не было               │
│ Дальше действует: harness (Проверки) │ │ Дальше действует: вы                 │
│ Вопросы по задаче (1)                │ │ Вопросы по задаче (1)                │
│  [важность 6] Какую библиотеку дат…  │ │  [важность 8] Какой разделитель…     │
│  Что изменится: …; ответил ведущий … │ │  Что изменится: …; только вы.        │
│ Весь процесс   ▸ подробности         │ │ Весь процесс   ▸ подробности         │
└──────────────────────────────────────┘ └──────────────────────────────────────┘
 Ещё не переданы в harness (2) — из `scope`, если он есть
 Ревью плана и договоров (1) — предметы ревью без работы
```

- Одна карточка на работу (`taskCards`, `src/model/tasks.ts`): что
  происходит сейчас (этап и сколько идёт; причина ожидания словами
  harness; «принята, больше ничего не нужно» с тем, где результат); после
  какой работы начнётся; примерный срок (§5.1); попытки «израсходовано
  N из M, осталось K» с полосой и строкой попыток harness; раунды ревью
  кода (`reviews[]` этой работы) и открытые блокирующие замечания; кто
  действует дальше (harness — этап …; вы; ведущий, затем вы; ждёт
  WEB-1; ждёт своей очереди; неизвестно); вопросы этой задачи целиком, с
  тем, кто отвечает и кто ответил. Ссылка «Весь процесс» открывает §5.2.
- Остановка, которая ждёт ведущего сейчас (`stage.needs` — ведущий) и
  не засчитана (ревизия 4: `lastFailure.kind: needs-lead`, `counted:
false`; `leadStopOf`): «Ждёт ведущего: работа остановилась до
  результата. Попытка не засчитана.» и фраза harness в скобках — подвид
  не угадывается. Если работа уже ждёт другого (например, вашего сброса),
  прошлый отказ — только строка истории; строка
  последнего сбоя — словами harness с «попытка засчитана / не
  засчитана», когда harness это говорит. Этап `plan-review` (ревью плана
  в живом `harness run`) — «Ревью плана», карточка «Идёт работа» и
  «Дальше действует: harness».
- Исполнитель остановился из-за окружения (harness alpha.59, признаки —
  §4): карточка пишет «Ждёт ведущего: окружение не дало исполнителю
  выполнить нужный шаг. Попытка не засчитана.» (harness такую попытку
  никогда не засчитывает); слова исполнителя («listen EPERM …») — в
  «подробностях»; в «Проблемах по ходу» — то же с «действует: ведущий».
  Обычный сбой окружения, остановка предпроверки или согласование
  заново так не читаются.
- Порядок: идут сейчас, ждут ответа, остановлены, ждут другую работу, в
  очереди, прочие ожидания, принятые, отменённые.
- Ниже: задачи из `scope`, ещё не переданные в harness (или пометка, что
  эта версия harness их не сообщает), и предметы ревью без работы (план,
  договор) — карточкой `ReviewSubjectCard` с раундами, замечаниями и
  эскалациями.
- `#/reviews` открывает `#/tasks` (заменой адреса). Компонент `Reviews`
  остаётся в API встраивания для хостов, которые его показывают.

### 5.6 Настройки (`#/settings`, только чтение)

Группы экрана:

- **Кто работает**: роли, затем runtime, модель и effort writer.
- **Кто проверяет**: план, договор и код — у каждого reviewer, запасные и
  правило вендора.
- **Когда спрашивать вас**: порог ввода словами («вопросы важности 7 и выше
  ждут ответа; ведущий может ответить до 4»), строка «Технические вопросы
  решает ведущий: да/нет; вопросы, меняющие результат для пользователя, —
  всегда вам» (из `leadAnswersTechnical`; отсутствие — «нет») и число
  критических путей.
- **Пределы**: попытки, бюджет исправлений, предел раундов ревью и раунды до
  эскалации.
- **Бюджеты**: по областям и что происходит при неизвестной цене.
- **Таймауты**: прогон, аренда, нижняя граница gate, пороги тишины и
  зависания с действием.
- **Слой lean** и параллельность.

У каждого значения видна единица. «По умолчанию» стоит только у путей из
`settings.defaulted`. Для каждой пары роли и репозитория виден действующий
reviewer кода и откуда он взят. При 390 px это одна колонка списков
определений. Дайджест политики — в подвале.

### 5.7 История (`#/history`)

Четыре графика с общей осью времени:

1. Нагрузка: пик одновременных попыток в интервале стопкой, пунктир на
   уровне `concurrency`.
2. Начатые и неудачные попытки в час.
3. Пройденные и проваленные gates.
4. Накопленные расходы против линии бюджета. Кривая пунктирная и подписана
   «нижняя граница», когда `spendBound` равно `lower`.

Над графиками — панель «Итоги окна» из `history.totals`: начато и
неудачных попыток (неудачные — по причинам), проверки, раунды ревью по
видам, расход за окно с границей, время, когда шли попытки, сумма времени
попыток и пик нагрузки. У каждой строки своё «что это значит», у расхода —
ещё и его граница («≥» или «неизвестно»). Граница кривой расходов — более
осторожная из `spendBound` и `totals.spendUsd.bound`: окно без известной
цены ни одного вызова — «неизвестно», а не «≥ $0.00»; тогда кривая не
рисуется, а таблица данных пишет «неизвестно». Без итогов (harness
alpha.55) панель так и пишет.

Окно по умолчанию — 24 ч; переключатель на 7 дней работает, только когда
производитель отдаёт это окно. При 390 px графики идут друг под другом во
всю ширину высотой 120 px с тремя подписями оси.

### 5.8 Здоровье (`#/health`)

Экран говорит обычными словами, с кодом рядом:

- «Контроллер работает, аренда до 12:00» / «Контроллер не запущен — работа
  не продвигается»;
- «Зависших попыток нет» / «Зависла 1 попытка» и «Тихих попыток: N» со
  ссылками на детали работы;
- «Сбоев окружения за 24 ч: N»;
- состояние бюджета: «потрачено ≥ $6.02 из $40, в пределах»;
- дрейф: «Изменено после приёмки: N; не проверено: M» и строки (ref,
  принято → голова, коммиты и файлы после, расхождение);
- предупреждения: фраза и код;
- версии: harness, UI, представление и состояние.

При 390 px — одна колонка.

### 5.9 Общие правила

- **Состояния.** У каждого экрана их четыре:
  - Загрузка.
  - Пусто: «Состояния пока нет — сначала выполните `harness run`».
  - Несовместимо: сообщение `checkView`.
  - Связь потеряна: последнее представление остаётся на экране с баннером.
- **«Что это значит».** У каждого термина (этап, gate, ревью, перепроверка,
  нейтральный сбой, нижняя граница, эскалация, принято, дрейф) есть
  раскрываемое пояснение «что это значит» из глоссария (§12). Пояснение —
  `<details>`, а не форма и не всплывающее окно.
- **Слова с основанием.** «Проверено» не пишется без того, как и кем;
  «готово» (принято) — без того, где принято (локально или в удалённом
  репозитории) и после каких проверок; «заблокировано» — без причины и
  того, кто должен действовать.
- **Неизвестное — не ноль и не «в порядке».** Отсутствующее поле,
  неизвестная граница или `unavailable` показываются словами «неизвестно»
  или «не проверено» и никогда как 0, «нет» или зелёный значок.
- **Доступность.** Цвет никогда не единственный сигнал; у каждого значка
  есть текст. Фокус виден. Live-регионы объявляют только число ждущих
  вопросов.
- **Тёмная тема.** `prefers-color-scheme`, переопределяется `data-theme` на
  корне.
- **Язык.** Русский и английский с S2 (`lang`, §6, §7). Коды, id и команды
  не переводятся.

## 6. Отдельный запуск

```sh
npx devcontour-harness-ui --view view.json          # голое представление или конверт `harness view`
npx devcontour-harness-ui --demo                    # встроенный пример
npx devcontour-harness-ui --state <dir> [--policy <file>] [--harness <bin>] [--lang ru|en]
npx devcontour-harness-ui --from http://127.0.0.1:4791/              # срез S3, уже запущенный serve-view
npx devcontour-harness-ui --demo --lang ru          # срез S2, язык интерфейса
```

**Язык (S2).** `--lang ru|en` задаёт язык интерфейса. Без флага язык берётся
из системной локали: первая непустая из `LC_ALL`, `LC_MESSAGES`, `LANG`;
значение, начинающееся с `ru`, даёт `ru`, любое другое — `en`. Русский —
полноправный язык, а не перевод по остаточному принципу. Приложение также
учитывает `?lang=ru|en` в адресе страницы; параметр адреса сильнее флага.

Язык интерфейса передаётся и источнику представления: приложение запрашивает
`GET /api/view?lang=<язык>`, а маршрут `--state` вызывает `harness view
--lang <язык>`, поэтому тексты harness приходят на том же языке, что и
подписи панели. Запрос без `lang` получает язык `--lang` CLI (или локали).
`--lang` передаётся harness, только если его `capabilities` объявляет `lang`
у операции `view`. Для `--view <file>` язык текстов выбрал тот, кто записал
файл.

**Окно истории (S3).** `--window 24h|7d` передаётся в живые маршруты
(`--state`, позже `--from`) как есть; только если `capabilities` объявляет
`window` у операции `view`, иначе CLI отказывает с `HARNESS_VIEW_UNAVAILABLE`. По умолчанию окно 24 ч, 7 дней — по запросу.
Для `--view` окно задаёт тот, кто записал файл.

**Контракт обмена.** Один контракт покрывает и CLI панели, и предложенный
`harness serve-view` (P3), поэтому `httpViewSource` работает с обоими.

- `GET /api/view` возвращает голое представление с содержательным `ETag` и
  `cache-control: no-store`.
- `GET /api/work/<id>` (и равнозначный `GET /api/view?work=<id>`) возвращает
  документ деталей работы (§3.11) с тем же `?lang=`, таймаутом и отказами,
  что у `/api/view`. Маршрут `--state` запускает `harness view --work=<id>`;
  id проверяется по алфавиту id графа (`[A-Za-z0-9_-]{1,80}`), иначе 404.
  У файла `--view` деталей нет (503 `VIEW_UNAVAILABLE`); `--demo` отдаёт
  встроенные детали двух работ и русские тексты harness для `?lang=ru`.
- `GET /api/events[?lang=][&work=<id>]` — поток SSE (S3). Данные каждого
  события — один объект JSON; `token` — дайджест содержимого (§6
  «Обновления»), а не `source.token`:
  - `event: view` `{token, checkedAt}` — дайджест отличается от последнего
    отправленного (первое событие потока — тоже `view`);
  - `event: fresh` `{token, checkedAt}` — живой маршрут проверил снова, то же
    содержимое; у файла — только первая удачная проверка после сбоя;
  - `event: stale` `{code, message, since, checkedAt}` — проверка не удалась
    (отказ harness, сбой, таймаут, файл не читается); `since` — первый сбой
    подряд;
  - `event: ping` `{}` каждые 15 с, чтобы страница отличала мёртвый поток.

  Не больше 32 потоков на сервер, лишний получает 503. Неизвестный `work`
  — 404, работа без документа деталей у файла — 503.

- `GET /api/health` возвращает `{ok, version, readOnly, live, lang?}`; `live` — `state` (живой `harness view`) или `file`.

Лента активности пока входит в документ обзора (`activity[]`, 50 последних
записей). Отдельный маршрут `GET /api/view?activity=1` с более длинным
окном — вариант, который остаётся открытым решением (§11).

Отказы:

- 409 `{error:{code,message}}`, когда представление несовместимо.
- 503 `VIEW_UNAVAILABLE`, когда представления ещё нет.

`--view` принимает либо голое представление, либо конверт ровно в том виде,
в каком его печатает `harness view` (`{ok:true,data}`). Конверт ошибки
считается `NOT_A_VIEW`.

**Вывод.** Когда панель начала слушать, в stdout уходит одна строка JSON:
`{"ok":true,"url":"http://127.0.0.1:4790/","port":4790,"readOnly":true,"version":…}`.

- Отказ печатает `{"ok":false,"error":{code,message}}`.
- Коды выхода совпадают с harness: 2 — неверный ввод, 3 — отказ,
  4 — инфраструктура.
- Подсказки для человека идут в stderr.

**Порт.** Без `--port` CLI перебирает 4790–4809 и берёт первый свободный.
Занятый явный `--port` — ошибка `PORT_BUSY`; молча на другой порт CLI не
переключается.

**Адрес.** По умолчанию CLI слушает `127.0.0.1`; также допустимы `::1` и
`localhost`. Любой другой адрес, включая `0.0.0.0` и `::`, — ошибка
`HOST_NOT_LOOPBACK`, и никакой флаг этого не отменяет.

**Обработка запросов.**

- Обслуживаются только GET и HEAD; на всё остальное — 405.
- Некорректный путь или байт NUL — 400.
- Сбой обработчика — 500, сервер при этом продолжает работать.
- Статические файлы должны оставаться внутри каталога приложения; это
  проверяется и по лексическому пути, и по реальному, поэтому символические
  ссылки не выводят за его пределы.

**Путь данных.**

- `--view`: файл перечитывается при каждом запросе.
- `--state <dir> [--policy <file>]`: CLI на старте читает `harness
capabilities`. Если в каталоге нет операции `view` (harness старше
  `0.1.0-alpha.55`) или harness не запускается, CLI отказывает с
  `HARNESS_VIEW_UNAVAILABLE` (выход 2) и подсказкой про `--view <file>`.
  Иначе каждый `GET /api/view` запускает `harness view --state <dir>
[--policy <file>] [--lang <язык>]` и отдаёт `data` его конверта;
  одновременные запросы одного языка делят один запуск. Отказ harness
  (конверт ошибки, ненулевой выход) — 503 `VIEW_UNAVAILABLE` с кодом и
  сообщением harness. Флага `--json` нет: harness печатает JSON по
  умолчанию.
  - Представление всегда вычисляет harness, установленный пользователем,
    а не этот пакет. `--harness <bin>` задаёт исполняемый файл (по
    умолчанию `harness` из PATH).
  - Позже (P3) маршрут перейдёт на `harness serve-view` дочерним процессом
    с прокси `/api/*` и SSE; договор `/api/view` не меняется.
- `--from <url>` (S3, ещё не сделано: в harness `0.1.0-alpha.55` нет
  `serve-view`) проксирует к уже запущенному `serve-view`. Адрес
  проверяется до первого запроса:
  - схема должна быть `http:`;
  - хост должен быть литералом `127.0.0.1` или `[::1]`, либо `localhost`,
    разрешённым в loopback-адрес;
  - в адресе не должно быть учётных данных;
  - путь должен быть `/` или пустым.
- Прокси не следует перенаправлениям и отвергает любой ответ, у которого
  адрес собеседника сокета не loopback.

**Без телеметрии.** Нет аналитики, запросов шрифтов или CDN и проверки
обновлений. Сборка самодостаточна.

**Обновления (S3).** У harness `0.1.0-alpha.55` нет канала изменений
(`serve-view` — предложение P3), поэтому изменения замечает сам CLI панели и
отправляет их странице по `/api/events`:

- **Только пока страница открыта.** Наблюдение за документом существует,
  пока его держит хотя бы один поток. Без потоков нет ни таймеров, ни `stat`,
  ни запусков harness: панель без открытой страницы не тратит процессор.
- **Подсказка и проверка.** Каждую 1 с сервер сравнивает дешёвую подпись
  файлов (mtime, размер, inode): у `--state` — каталога состояния,
  `state.sqlite`, `state.sqlite-wal` и файла политики, у `--view` — самого
  файла. Изменение подписи сразу запускает проверку: у `--state` — `harness
view`, у `--view` — чтение файла.
- **Дайджест.** Изменение определяет идентичность содержимого. С ревизии
  представления 1 (harness `0.1.0-alpha.56`, предложение P8) это сам
  `source.token` (`harness:` и SHA-256 строки токена — так любая строка
  безопасна для заголовка и одинакова в SSE и `x-hui-digest`): harness хеширует содержимое без часов
  проекции и сам меняет токен, когда от часов зависит содержимое (аренда,
  живость, запись вышла из окна или переехала в соседний интервал). Язык и
  работа, от которых токен ещё зависит, разделены ключом наблюдения. Подписи
  окна истории при этом не двигаются, пока не изменилось содержимое: строка
  свежести говорит «без изменений с HH:MM». У ревизии 0 (`0.1.0-alpha.55`)
  токен хеширует и границы окна и разный при каждом запуске, поэтому панель
  считает свой дайджест: SHA-256 документа без `generatedAt` и
  `source.token`, с границами окна, обрезанными до минуты (неизменное
  состояние — тот же дайджест в пределах минуты). Пустой токен ревизии 1
  тоже получает этот дайджест (документ без строки `source.token` проверка
  панели отклоняет). Дайджест файла — SHA-256 всех байтов
  (время снимка — его содержимое). `GET /api/view` и `/api/work/<id>`
  отдают дайджест в заголовке `x-hui-digest`; `ETag` — хеш байтов ответа.
- **Интервал с отступлением (`--state`).** Без изменения подписи сервер
  перепроверяет через 2 с, затем через 4, 8 и 15 с, пока ничего не меняется;
  изменение возвращает 2 с. Пока в представлении есть работающие попытки
  (`progress.running > 0`), интервал не больше 5 с: аренды и живость меняются
  без записи в хранилище (§3.10). Неудачная проверка тоже отступает. Файл
  `--view` проверяется только по изменению подписи.
- **Повторное использование.** `GET /api/view` в течение 1,5 с после
  удачной проверки берёт её результат, а не запускает harness ещё раз (не
  больше 64 таких результатов, отказы не хранятся). Проверка, которая ждёт
  свободного места среди `MAX_RUNS` запусков, не запускается, если её
  наблюдение уже закончилось.
- **Медленный читатель.** Поток, у которого не отправлено больше 64 КБ,
  закрывается, а не копит события.
- **Восстановление.** Первая удачная проверка после сбоя всегда даёт событие
  (`view` или `fresh`), даже у файла с прежним содержимым.
- **Страница.** Пока поток не прислал первое событие, страница опрашивает
  `GET /api/view` каждые 5 с. Получив `view` с токеном, отличным от токена
  документа на экране (его `x-hui-digest`), она загружает документ; `fresh`
  с тем же дайджестом только обновляет время проверки. Неудачная загрузка
  повторяется опросом раз в 5 с, пока не удастся, даже когда поток жив; так
  же повторяется и первый отказ `VIEW_UNAVAILABLE`. Загрузки идут по одной
  (запрос во время загрузки — ещё одна загрузка после неё); подтверждение
  показанного содержимого и скрытие вкладки отменяют ответ загрузки, которая
  ещё идёт. Загрузка без ответа 40 с считается неудачной и повторяется опросом. Скрытая вкладка не опрашивает никогда.
  Экран работы держит только поток деталей: поток обзора на нём закрыт. Ошибка потока или 45 с тишины (нет даже `ping`) — страница
  закрывает поток, переходит на опрос раз в 5 с и пробует поток снова через
  30 с. Скрытая вкладка закрывает поток и останавливает опрос; при показе
  страница сразу загружает документ и открывает поток.
- **Свежесть.** Над экраном строка «Данные на HH:MM · обновляются сами»
  (`--state`), «… · снимок; при изменении файла страница обновится»
  (`--view`) или «… · проверка раз в 5 секунд» (опрос). Время — `generatedAt`
  документа или, у `--state`, более позднее время проверки того же
  содержимого («без изменений с HH:MM»). Когда проверка не удалась (`stale`
  или 503 после удачного документа), над ней предупреждение «Не удалось
  обновить данные с HH:MM: <причина>. На экране данные на HH:MM — они могут
  быть устаревшими»; неизвестное не показывается свежим.
- **Встраивание.** `ViewSource.subscribe(onChange, {workId?})` передаёт
  `LiveEvent` (`view`, `fresh`, `stale`, `down`); вызов `onChange()` без
  события значит «загрузите снова». `httpViewSource` даёт `subscribe`, только
  когда есть `EventSource`.

Измерения (macOS, harness `0.1.0-alpha.55`, пустое состояние, `harness view`
≈ 0,25 с процессора) — в описании ветки; без страницы панель за 120 с не
запустила harness ни разу.

**Совместимость (`--check`, S3).** `devcontour-harness-ui --check [--harness
<bin>] [--state <dir> [--policy <file>]]` запускает `harness --version`,
`harness capabilities` и, с `--state`, один `harness view`, затем печатает
одну строку `{ok, harness, ui, viewVersion, uiViewVersion, compatible, fix?,
view?}`. `viewVersion` берётся из выходной схемы операции `view` в каталоге
(или из прочитанного представления); не объявленная версия — `null` и
`compatible: false`, пока не прочитано представление. Выход 0 — совместимо,
3 — нет (с `fix`). Отказ harness на этом состоянии при совпадающих версиях
— `compatible: true` с `fix` и `view.ok: false`.

## 7. API встраивания (DevContour)

DevContour подключает `devcontour-harness-ui` как точную зависимость
времени сборки и собирает компоненты через Vite. Нет ни микрофронтенда во
время выполнения, ни iframe, ни второго сервера.

```ts
import {
  Overview,
  WorkDetail,
  Tasks, // alpha.4: replaces Reviews in the panel
  Reviews,
  Settings,
  History,
  Health, // S2
  Decisions, // S2
  Activity, // S2
  type OperatorView,
  type ViewSource,
  checkView,
} from 'devcontour-harness-ui';
import 'devcontour-harness-ui/styles.css';

interface ViewSource {
  load(signal?: AbortSignal): Promise<ViewCheck>;
  subscribe?(onChange: () => void): () => void;
}
```

- **Данные.** Компоненты получают `view: OperatorView` через prop и сами
  ничего не запрашивают. Загрузкой владеет хост. DevContour реализует
  `ViewSource` поверх своего хранилища. Это можно сделать двумя способами:
  - Вызывать на сервере `operatorView(collectOperatorViewInput(...))` из
    пакета harness внутри той же транзакции, что и для `statusOf`, и
    отдавать результат по своему `/api/harness/view`.
  - Или отображать свои существующие сводки в тип представления. Только
    первый способ сохраняет числа идентичными `harness view`, поэтому
    рекомендуется он.
- **Навигация.** Компоненты принимают обратные вызовы (`onOpenWork(id)`,
  `onOpenReview(subject)`) и никогда не трогают `location`. Отдельное
  приложение связывает их с hash-маршрутами, DevContour — со своей
  навигацией через строку запроса.
- **Оформление.** Каждый цвет, радиус, шрифт и отступ — custom property
  `--hui-*`, объявленная только на `:root`; DevContour сопоставляет свои
  токены на обёртке, например `--hui-accent: var(--data-accent)` и
  `--hui-bad: var(--status-failed)`. С alpha.4 компоненты свёрстаны на
  Tailwind CSS 4 и shadcn/ui, но **хосту Tailwind не нужен**:
  `styles.css` уже собран, утилиты имеют префикс `hui:`, preflight нет,
  каждое правило ограничено `.hui`/`.hui-…` (§5.0), а Radix и
  скопированные компоненты shadcn/ui собраны в пакет (`dist/lib/vendor`).
  Во время выполнения пакету нужен только React (`peerDependencies`);
  `tests/package.test.ts` собирает библиотеку и проверяет, что она
  импортирует только `react`, `react-dom`, `react/jsx-runtime` и `node:*`.
  Наши правила лежат в своих слоях (`hui-theme, hui-base, hui-components,
hui-utilities`, `hui-properties`): слои хоста с теми же короткими именами (`base`,
  `utilities`) с ними не сливаются и не меняют их порядок, классы не
  пересекаются (`hui:`). Неслоёные стили хоста по правилам каскада сильнее
  любого слоя: глобальный сброс без слоя (`* { border-width: 0 }`,
  `h3 { margin }`) действует и внутри панели — такой сброс хосту нужно
  держать в своём слое (как это делает Tailwind 4) или не применять внутри
  `.hui`. Токены `:where(:root)` не в слое: хост переопределяет их на
  обёртке, а не на `:root` внутри своего слоя. Глобальны только регистрации `@property --tw-*` — такие же, как у
  самого Tailwind. Тема: `Settings` принимает `theme` и `onThemeChange`;
  без `onThemeChange` блок «Оформление» не показывается, и тему задаёт хост
  (`data-theme` на `<html>` или свои значения `--hui-*`).
- **Язык и подписи.** Компоненты двуязычны с S2: prop `lang: 'ru' | 'en'`,
  по умолчанию `ru`. Все подписи — из одного словаря (`src/model/dict.ts`);
  тест проверяет, что у обоих языков есть каждый ключ. Частичный словарь
  `labels`, которым хост переопределяет отдельные подписи, остаётся в S4.
- **Запись.** Форма ответа S5 принимает обратный вызов `onAnswer(requestId,
version, answer)`. Запись выполняет хост со своими правилами CSRF и
  actor. Компонент сам ничего не отправляет.

## 8. Что переезжает из DevContour и что остаётся

Общие для harness части переезжают сюда как компоненты, работающие от
представления. Каждая заменяется в DevContour компонентом пакета, когда
срез этого компонента готов.

| Часть DevContour (src/web)                                                                           | Куда                                               | Срез |
| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ---- |
| Плитка «harness» на главной: слоты, попытки за 24 ч по видам, падающие gates, бюджет, расход, сервер | `Health` + полоса Overview                         | S2   |

`CheckPanel` переедет только как более поздняя ревизия представления с
разделом проверок, когда договор property-check устоится.

В DevContour остаются:

- плитки подготовки продукта (продукт, архитектура, дизайн);
- релизы, ChangeSets и покрытие;
- доска и строки процесса ChangeSet;
- подписи продуктового журнала;
- редактируемые формы моделей и порога (они пишут конфигурацию workspace
  DevContour через его собственный двухшаговый preview/apply);
- живой хвост активности прогона (`api/runs/:id/activity`), который несёт
  вывод исполнителя и не входит в представление;
- токены раскладки (боковая панель, инспектор, холст).

Связи, которые нужно разорвать по пути:

- Компоненты сами запрашивают `/api/...`; они будут получать данные через
  props.
- Типы импортируются из `core/model.ts`; они будут браться из типа
  представления.
- Подписи зашиты в код.
- Стили опираются на классы Tailwind; они перейдут на переменные `--hui-*`.

## 9. Безопасность

**Сеть.**

- Панель слушает только loopback (§6), и ничто этого не отменяет.
- Заголовок `Host` каждого запроса должен называть loopback-слушателя:
  `127.0.0.1:<port>`, `localhost:<port>` или `[::1]:<port>`. На всё
  остальное — 421; это защищает от DNS rebinding.
- Цель прокси `--from` ограничена loopback, перенаправления не
  выполняются (§6).
- Состояние удалённого репозитория (`target.remote`) читается только из
  локальной remote-tracking ссылки. Ни панель, ни harness не запускают
  `git fetch` и не обращаются к удалённому репозиторию.

**Заголовки ответа.**

- `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`
- `X-Frame-Options: DENY`

**Статические файлы.** Файл должен оставаться внутри каталога приложения и
по лексическому, и по реальному пути. Символическая ссылка за пределы
каталога получает 404, некорректный путь — 400. Оба правила покрыты
тестами.

**Граница доверия.** Маскирование, обрезку и пределы обеспечивает
производитель (проекция harness, P1). Гейт панели `checkView` проверяет
только поля, которые читают компоненты, и не маскирует заново. Поэтому
`--view <file>` раздаёт файл как есть: панель открывает только тот файл,
которому оператор доверяет как выводу `harness view`, и только на
loopback. Пока P1 не выпущен, свободные тексты в представлении ничем,
кроме производителя, не защищены.

**Чего в представлении никогда нет.**

- промптов, вывода исполнителя, логов и путей к логам;
- переменных окружения и токенов;
- команд gates и профилей инструментов;
- абсолютных путей: домашний каталог становится `~`, пути внутри
  репозитория становятся относительными к нему, любой другой абсолютный
  путь заменяется на `‹path›`;
- текстов находок и вопросов сверх маскированного и обрезанного заголовка.

**Маскирование.** Оно применяется к каждому свободному тексту
представления, а не только к заголовкам:

- заголовки;
- `progress.queue.detail`;
- `warnings[].message`;
- `drift[].unavailable`;
- `stage.step`;
- поля `line`;
- `attempts.lastFailure.plain`;
- `blockers[].plain`;
- `questions[].plain`;
- `activity[].plain`;
- `decisions[].title`, `decisions[].reason` и `decisions[].revisit`;
- `target.remote.reason` и `target.remote.line`.

Секрет может разрезаться пополам на границе обрезки и проскочить, поэтому
маскирование выполняется **до** обрезки. Шаг маскирования:

1. Заменяет похожие на токены строки на `‹masked›`. Это префиксы ключей
   провайдеров, `Bearer …`, длинные последовательности base64 или hex и
   `user:pass@` в URL.
2. Заменяет домашний каталог на `~`, путь внутри репозитория — на
   относительный, другой абсолютный путь — на `‹path›`.
3. Обрезает текст до предела поля (§3.10).

`--no-titles` убирает заголовки, `queue.detail` и заголовки находок, как
это делает `report --no-titles`.

Тесты P1 подкладывают ключ провайдера, bearer-токен, учётные данные в URL,
домашний и посторонний абсолютный путь в заголовок работы, вопрос, находку,
ошибку попытки, которая попадает в `queue.detail` и `lastFailure.plain`,
ошибку git, которая попадает в drift и `target.remote.reason`, текст
вопроса для `questions[].plain`, событие для `activity[].plain` и причину
решения для `decisions[].reason`. В одном
случае ключ стоит поперёк границы обрезки. Во всех случаях байты
представления не должны содержать ни одного подложенного значения.

**Путь записи (S5).**

Дизайн S5 ждёт одобрения владельца; до него путь записи не реализуется.

Источник (origin) один. Браузер общается только с CLI панели. CLI панели
проксирует `POST /api/answers` и `GET /api/questions/<id>` к своему
дочернему `serve-view`. Поэтому `connect-src 'self'` соблюдается, и браузер
никогда не делает запросов на другой порт.

Браузер аутентифицируется одноразовым кодом, который обменивается на
сессионную cookie:

- Когда запись включена, CLI панели печатает URL с одноразовым кодом во
  фрагменте (`#code=…`).
- При первой загрузке приложение один раз отправляет код в теле `POST
/api/session`.
- Сервер отвечает cookie `HttpOnly; SameSite=Strict; Path=/api` и
  аннулирует код.
- Приложение убирает фрагмент через `history.replaceState`.
- Код, утёкший в лог или чат, после первого обмена бесполезен.
- Коды истекают через 10 минут. Обычные строки лога код не печатают;
  печатает только одна стартовая строка.

У CLI и `serve-view` есть отдельный общий секрет:

- CLI панели генерирует случайный 32-байтовый секрет.
- Он передаёт секрет дочернему `serve-view` через его stdin, никогда через
  argv, окружение или stdout.
- Он отправляет секрет как `Authorization: Bearer` в каждой проксируемой
  записи.
- `serve-view --allow-answers` читает секрет из stdin и принимает записи
  только с ним.

Каждая запись также должна пройти проверки:

- сессионная cookie;
- `Origin`, равный origin панели;
- `content-type: application/json`;
- тело не больше 16 КБ.

Что возвращает проваленная проверка:

| Сбой                                  | Ответ |
| ------------------------------------- | ----- |
| нет сессионной cookie или она неверна | 403   |
| неверный `Origin`                     | 403   |
| тело не JSON                          | 415   |
| тело больше 16 КБ                     | 413   |

**Договор ответа.** Тело запроса один к одному соответствует `harness
input-answer`:

```
{ requestId, requestVersion, kind: 'clarification' | 'requirement-change',
  optionId?, text }
```

- `text` обязателен, потому что его требует `answerInput`.
- `kind` по умолчанию `clarification`, только если пользователь ничего не
  выбрал.
- Прежде чем разрешить ответ, форма показывает полный контекст решения:
  - необрезанный (но маскированный) текст вопроса;
  - варианты с их последствиями;
  - серьёзность;
  - кто может ответить.

  Этот контекст она читает из аутентифицированного `GET /api/questions/<id>`.

- Harness записывает ответ с `actor: operator`. Устаревшая версия получает
  `REQUEST_VERSION_STALE`, и это показывается. Запросы, на которые оператор
  отвечать не может, и любой путь ведущего не открываются.
- Агенты никогда не используют этот путь, а skill запрещает отвечать за
  пользователя.

**Цепочка поставки.** Зависимости — точные версии. Сборка времени
выполнения содержит только React, а CLI импортирует только `node:*`.

## 10. Срезы

Каждый срез заканчивается зелёным `npm test && npm run typecheck && npm run
build`. Тесты не используют сеть дальше loopback, их фикстуры лежат в
`fixtures/`. Срез, который затрагивает harness, сначала попадает туда, по
правилам harness: независимая приёмка и предел раундов. Критерии приёмки
проверяют смысл на экране, а не только то, что отрисовка прошла.

**S0: каркас (первые коммиты этого репозитория).**

- Состав:
  - тип представления и `checkView`, который проверяет вложенные поля;
  - `ViewSource` с типизированными отказами 409;
  - Обзор с фразой в шапке и подвалом на русском и английском;
  - loopback CLI с `--view` (голое представление или конверт) и `--demo`;
  - пример-фикстура и навык.
- Приёмка и тесты (`tests/*.test.ts*`):
  - Отказы хостинга:
    - `0.0.0.0`, `::` и адреса LAN отклоняются;
    - занятый явный порт — ошибка;
    - чужой `Host` получает 421;
    - POST получает 405;
    - искажённый путь получает 400, и сервер продолжает работать;
    - выход по symlink получает 404.
  - Обработка представления:
    - несовместимое представление получает 409 и сохраняет сообщение через
      `httpViewSource`;
    - искажённые разделы отклоняются до отрисовки;
    - неизвестные значения читаются осторожно.
  - Отрисовка обзора:
    - спрашиваются только вопросы `awaiting-answer`;
    - число работающих берётся из `progress`, с пометкой об обрезке;
    - показывается худшая область бюджета и «бюджета нет», когда их нет;
    - дрейф, который не удалось проверить, не показывается как ноль;
    - фраза «Сейчас… От вас: …» и подвал «Данные harness на HH:MM; панель
      ничего не меняет» на русском, с английским запасным вариантом;
    - нет элементов форм.
  - Пользовательские свойства `--hui-*` объявлены только на `:root`.

**S1: схема в harness** (предложения P1, P2; поля P6.1–P6.4 — в alpha.55).

- Состав:
  - `operatorView` и `harness view` попадают в harness.
  - UI импортирует тип из `devcontour-harness/projections`.
  - Договорный тест проверяет каждую фикстуру по
    `schemas/operator-view.schema.json`.
- Набор фикстур:
  - пустое состояние;
  - занято, пауза от оператора;
  - бюджет работы превышен при общем в пределах;
  - большие расходы до окна;
  - эскалированное ревью;
  - дрейф, включая дрейф, который не удалось проверить;
  - вопрос в каждом состоянии ввода, один из них отвечает только оператор;
  - технический вопрос при `leadAnswersTechnical` и вопрос с `impact`
    `user-visible` при том же флаге;
  - повторная попытка с `lastFailure` каждой группы сбоя;
  - каждый код блокировки с `plain` и `actor`, включая `actor: null`;
  - работа с `verification[]` всех видов `how`;
  - все списки обрезаны;
  - более новая ревизия;
  - документ наибольшего размера.
- Приёмка:
  - Каждая фикстура проходит схему.
  - Представление примера harness `single-task` совпадает с выводом
    `harness view` байт в байт.
  - Числа совпадают с `status` и `report` на том же состоянии: попытки,
    нейтральный счётчик, перепроверки, границы расходов, gates (пропущенные
    и повторно использованные отдельно) и этап.
  - `lastFailure.plain` совпадает с причиной в строке этапа `status`.
  - Ревью кода даёт в `verification[]` строку с `how: read`, а не
    `executed`.
  - Тест подброшенных секретов проходит, включая ключ на границе обрезки.
  - Документ наибольшего размера даёт `VIEW_TOO_LARGE`; документ типичного
    размера — не больше 256 КБ (§3.10).
  - Токен содержимого меняется при истечении аренды без записи в хранилище.

  - hash-маршруты;
  - состояния «пусто», «несовместимо», «связь потеряна» и «новая ревизия»;
  - тёмная тема.
- Приёмка:
  - Для каждой фикстуры каждый экран показывает ожидаемый ключевой текст:
    счётчики, границы, исполнителей и состояния — на обоих языках.
  - Слова с основанием (§5.9) проверяются по строкам, а не по всей

    «нет» или «в порядке».
  - `blockers[]` с `actor: null` читается как «просто ждёт очереди — ничего
    не нужно».
  - Playwright при 1280 px и 390 px не показывает горизонтальной прокрутки.
  - axe не находит серьёзных нарушений.
  - У графиков есть текстовые сводки.
  - Накопительный график расходов начинается с `spendOpeningUsd`.
  - Нигде нет элемента `<form>`.
  - Браузерный тест подтверждает, что `--hui-*`, заданные на обёртке, меняют
    вычисленные цвета.
- Тесты:
  - `renderToStaticMarkup` для каждого экрана, фикстуры и языка;
  - один прогон Playwright против `--demo`.

**S5: ответы оператора** (предложение P4; дизайн записи утверждает
владелец, §11).

- Состав: форма ответа для вопросов `awaiting-answer`, на которые может
  ответить оператор, через прокси с одним origin из §9.
- Приёмка:
  - Ответ записан с `actor: operator`, версией запроса и `kind`.
  - До ответа видны полный замаскированный вопрос, его варианты и для
    каждого — что изменится для пользователя.
  - Устаревшая версия отклоняется и показывается.
  - Каждый отказ возвращает свой статус:
    - нет кода, код уже использован или нет cookie: 403;
    - неверный `Origin`: 403;
    - тело не JSON: 415;
    - тело больше 16 КБ: 413.
  - Код и общий секрет никогда не появляются в журналах, ответах
    представления и argv.
- Тесты:
  - серверные тесты на каждый отказ;
  - браузерный тест, который отвечает от начала до конца на fixture
    runtime;
  - компонентный тест, что без `onAnswer` форма ничего не делает.

## 11. Открытые решения

Решено владельцем (2026-11-19):

- **Язык.** Интерфейс двуязычный с S2: русский — полноправный, английский —
  запасной; `--lang ru|en`, по умолчанию из системной локали. Документация —
  на русском, как у harness; идентификаторы в коде — на английском.
- **Стоимость дрейфа в `serve-view`.** Кэш по голове цели, пересчёт не чаще
  раза в 30 с.
- **CheckPanel.** Пока остаётся в DevContour.
- **Окна истории.** 24 ч по умолчанию, 7 дней по запросу. Более длинные
  окна потребовали бы предварительной агрегации в harness.
- **Дом пакета.** Остаётся отдельным репозиторием.

Открыто:

1. **Первая запись.** S5 ждёт утверждения владельцем дизайна с одним
   origin: одноразовый код, cookie и секрет, переданный дочернему процессу
   через stdin.
2. **Маршрут ленты действий.** Сейчас `activity[]` (50 последних) входит в
   документ обзора. Альтернатива — отдельный документ `GET
/api/view?activity=1` с более длинным окном и постраничным чтением; тогда
   лента не раздувает обзор.
3. **Наблюдаемое время по умолчанию.** Показывать ли `stage.typical` сразу
   или только по раскрытию; минимальное число образцов (предложено 5) и
   окно, по которому оно считается (всё состояние или последние 7 дней).
4. **Удалённый репозиторий — только локально.** Состояние берётся из
   локальной remote-tracking ref без fetch, поэтому оно может отставать.
   Решить, достаточно ли подписи «по последнему обновлению git на этой
   машине» или нужен явный возраст ref (время последнего fetch из reflog).

5. **Пределы списков и 256 КБ.** Наибольший документ при нынешних
   пределах больше 256 КБ (§3.10). Решить: уменьшить пределы (например,
   общий предел замечаний в обзоре) или оставить отказ `VIEW_TOO_LARGE`
   для крайних состояний.
6. **Язык текстов harness** — решено в `0.1.0-alpha.55`: опция проекции
   `lang: 'ru' | 'en'` (`harness view --lang`), шаблоны на обоих языках в
   harness, детали из внешнего вывода не переводятся. Приложение передаёт
   язык интерфейса источнику (`GET /api/view?lang=`, §6).

## 12. Глоссарий

Тексты «что это значит» на экране берутся отсюда.

| Термин                   | Что это значит                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Этап                     | Шаг, на котором сейчас работа: очередь, подготовка, написание, проверки, ревью, интеграция, ожидание ответа.                                                                                                                                                                                                                                                                  |
| Ведущий (lead)           | Агент, который ведёт проект от вашего имени: запускает harness, читает результаты, отвечает на вопросы, которые ему разрешены.                                                                                                                                                                                                                                                |
| Исполнитель, writer      | Агент, который пишет код одной работы в отдельной копии репозитория.                                                                                                                                                                                                                                                                                                          |
| Reviewer, ревью          | Другой агент читает план или изменения и пишет замечания. Ревью кода читает diff и ничего не запускает, если это не сказано отдельно.                                                                                                                                                                                                                                         |
| Проверки, gates          | Команды проекта (тесты, lint, сборка), которые harness запускает над изменением. Результат пишется вместе со способом: запущено, взято прежнее, не проверялось.                                                                                                                                                                                                               |
| Перепроверка             | Повторный запуск проверки на той же попытке, чтобы отличить настоящую ошибку от случайной.                                                                                                                                                                                                                                                                                    |
| Попытка                  | Один заход исполнителя над работой. У работы ограниченное число попыток; прерывание при остановке попытку не расходует.                                                                                                                                                                                                                                                       |
| Нейтральный сбой         | Сбой не по вине кода (например, окружение), который не расходует попытку, но имеет свой предел.                                                                                                                                                                                                                                                                               |
| Интеграция               | Перенос принятого изменения в целевую ветку с проверками на результате.                                                                                                                                                                                                                                                                                                       |
| Принято                  | Работа прошла проверки и ревью, и harness записал результат в целевую ветку локально. «В удалённом репозитории» — отдельный факт: туда результат отправляет человек или ведущий по вашей просьбе.                                                                                                                                                                             |
| Дрейф                    | Целевая ветка изменилась после приёмки, и принятый результат стоит не на её вершине.                                                                                                                                                                                                                                                                                          |
| Эскалация                | Блокирующее замечание не решилось за несколько раундов ревью, и решение переходит к вам.                                                                                                                                                                                                                                                                                      |
| Временное решение        | Решение «пока так», с условием, когда к нему вернуться.                                                                                                                                                                                                                                                                                                                       |
| Технический вопрос       | Вопрос, ответ на который не меняет результат для пользователя. Его может решать ведущий, если это включено в настройках.                                                                                                                                                                                                                                                      |
| Нижняя граница (`≥`)     | Часть цен неизвестна, поэтому показанная сумма — минимум, настоящая может быть больше.                                                                                                                                                                                                                                                                                        |
| Неизвестно, не проверено | У harness нет сведений. Это не ноль и не «в порядке».                                                                                                                                                                                                                                                                                                                         |
| Контроллер               | Процесс harness, который сейчас ведёт очередь. Без него работа не продвигается.                                                                                                                                                                                                                                                                                               |
| Зависшая / тихая попытка | Попытка давно не подавала признаков жизни (тихая) или дольше порога (зависшая).                                                                                                                                                                                                                                                                                               |
| Ждёт очереди             | Работа ждёт свободного места или окончания работ, от которых зависит. Ничего делать не нужно.                                                                                                                                                                                                                                                                                 |
| Решение                  | harness остановил работу и сам её не продолжит: нужен человек или ведущий — сбросить попытки, согласовать план заново, увеличить бюджет и т. п. Это не вопрос: вопрос задаёт исполнитель, и в ответе нужно содержание, а решение — разрешение продолжать.                                                                                                                     |
| Ждёт другой работы       | Работа зависит от другой и начнётся, когда та будет принята. С ней самой делать ничего не нужно — действовать нужно по той работе, кто там указан.                                                                                                                                                                                                                            |
| Кто и почему ответил     | Кто дал последний ответ на вопрос исполнителя: вы, ведущий или хост. Ведущий отвечает только по правилу из настроек и записывает причину; её показывает harness.                                                                                                                                                                                                              |
| Причина неудачи          | Группа, к которой harness отнёс неудачную попытку: ошибка в коде, окружение, время вышло и другие. Числа по группам складываются в число неудачных попыток.                                                                                                                                                                                                                   |
| Раунд ревью              | Одно прочтение плана, контракта или изменений reviewer и его ответ с замечаниями. Повтор вызова после сбоя отдельным раундом не считается.                                                                                                                                                                                                                                    |
| Время, когда шли попытки | Сколько времени окна хотя бы одна попытка работала. Две попытки одновременно считаются один раз.                                                                                                                                                                                                                                                                              |
| Сумма времени попыток    | Время всех попыток окна, сложенное: две попытки по часу одновременно дают 2 ч.                                                                                                                                                                                                                                                                                                |
| Расход за окно           | Стоимость вызовов агентов, которые harness относит к окну, по правилам своего отчёта. «≥» — у части вызовов цена или учёт неизвестны или неполны; «неизвестно» — ни у одного вызова окна нет известной цены.                                                                                                                                                                  |
| Пик нагрузки             | Наибольшее число попыток, которые шли одновременно в окне; сравнивается с числом мест.                                                                                                                                                                                                                                                                                        |
| Обычное время этапа      | Сколько этап занимал раньше в этом состоянии (не меньше пяти замеров): половина укладывалась в первое число, девять из десяти — во второе. Наблюдение, а не обещание.                                                                                                                                                                                                         |
| Вы, оператор             | Человек, для которого идёт работа. Отвечает на вопросы, которые меняют результат для пользователя, и решает эскалации.                                                                                                                                                                                                                                                        |
| Хост                     | Программа, внутри которой запущен harness (например, DevContour). Может ответить на вопрос исполнителя от своего имени по своим правилам.                                                                                                                                                                                                                                     |
| В удалённой ветке        | harness сверяет принятый коммит с копией удалённой ветки на этой машине (remote-tracking ref, например origin/main) — без сети и без git fetch, поэтому сведения могут отставать до следующего git fetch или git push здесь. Время рядом — когда git на этой машине последний раз обновил копию. «Неизвестно» — не «нет» и не «отправлено»; сам harness ничего не отправляет. |
